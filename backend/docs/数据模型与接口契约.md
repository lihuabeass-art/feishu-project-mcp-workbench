# 数据模型与接口契约

## 1. 三层结构与转换原则

```
MCP tools/call 载荷
   │  mcp/parse.rs（只认已见形状，不猜字段名）
   ▼
接口侧原始结构 model/raw.rs          ← 忠实保留响应：字符串/数字/布尔/null、未知字段进 raw
   │  model/domain.rs::to_work_item（不补造业务值；缺身份即拒绝）
   ▼
内部模型 WorkItem
   │  store.rs（UPSERT，派生列+原文并存）
   ▼
SQLite work_item 表
```

- **空串 / null / 缺失**只在派生列上统一为 `None`；`work_item.raw_json` 永远保留响应原样，
  派生列不足以表达的信息都从它找回。
- **不补造业务值**：响应没给的字段在内部模型就是 `None`，不会用类型默认值伪装出「待处理」这类业务态。

## 2. `work_item` 表（schema v1）

| 列 | 来源 | 依据 |
|---|---|---|
| `project_key`, `work_item_type_key`, `work_item_id` | `project_key` / `work_item_info.*` | **复合主键**。调查只证实响应含这三段，从未证实 `work_item_id` 跨空间/跨类型全局唯一（U3）。用单键的风险是串号覆盖（不可逆数据污染）；用复合键的代价只是「若 id 本就全局唯一，多存两列」。缺失段写入空串哨兵并记入 `identity_missing_flags` |
| `identity_missing_flags` | `missing_parts()` | 真实「哪段身份缺失」的存放处（JSON 数组文本） |
| `project_name`, `work_item_name` | 响应 | 空串归一为 `NULL` |
| `flow_kind` | 派生 | `node` / `state` / `both` / `none`，**由响应内容判定，不按类型键猜测**：`story→节点流`、`issue→状态流` 只是样本观察（U3 未证实可作规则）。两类信息都为空记 `none` |
| `node_name`, `node_state_key` | `node_info` | 节点流字段，原样保留 |
| `start_state_key_name`, `end_state_key_name` | `state_info` | 状态流字段。节点流与状态流**不折算成同一个「状态」字符串**（设计文档决策 4） |
| `schedule_start_raw`, `schedule_end_raw` | `schedule` | 只存响应原文。时间单位/时区/本地化转换未定（U4），不做换算 |
| `raw_json` | 整条响应条目 | 紧凑 JSON 原文 |
| `first_seen_at_ms`, `last_seen_at_ms`, `seen_count` | 本地 | 同步出现记录；当前清单归属由 `work_item_source` 维护（见 §4） |

## 3. `sync_run` 表（运行台账）

每次同步一行：`status`（`running|success|failed`）、`pages_fetched`、`items_received`
（含被拒绝条目：接口给了多少算多少）、`items_upserted`、`items_rejected`、
`remote_total`（服务端最后声明的 total，不自行折算）、`stop_reason`、
`error_kind`（12 类错误短码，见 §5；另有 `incomplete` 专用于 max_pages 截断——它不是错误类，
而是「无错误但不完整」的台账标记）、`error_message`（经脱敏）、`rejection_detail`
（按原因码聚合的 JSON：code/count/sample，样本截断）。

**v3 新增列**：`trigger`（`manual|automatic`）、`source_id`（本轮实际用的来源）、
`items_out_of_scope`（收到了但被来源类型范围筛掉、因此没入库的条数）。最后一项与
`items_rejected` 分开计数——「范围筛掉」和「结构不符被拒」是两件事，混在一起就没法排查。
台账按 `sync_run_retention`（默认 0，即永久保留；桌面端始终永久保留）轮转，只删**已结束**的行；0 或负数 = 不清理。

**失败运行不冒充成功**：半途出错、被 `max_pages` 截断（`error_kind="incomplete"`）
都不占用 `last_successful_sync()`；已落库的页保留不回滚。唯一例外：收尾 UPDATE 自身失败时
台账可能残留一行 `running`（主错误优先返回，宁可留痕不可吞错），`running` 同样不占成功位。

## 4. 同步语义（与任务书二.5 对应）

| 要求 | 实现 |
|---|---|
| 重复同步不产生重复事项 | 复合键 `ON CONFLICT DO UPDATE`（UPSERT），`seen_count` 递增 |
| 同步失败不清空已有缓存 | 已取得的页保留，失败、截断或条目解析失败均不撤销来源归属 |
| 清单与来源最新结果一致 | 不存在更晚发起的同来源运行时，完整成功后按来源移除缺席事项；只有无任何来源归属的工作项才移出清单，不调用远端删除 |
| 提供最近成功同步信息 | `last_successful_sync()` 只查 `status='success'` 的最新一行 |
| 翻页终止可解释 | 带 `total` 时取到总数，提前空页报错；无 `total` 时取到空页，不再假定短页就是末页。`short_page` 仅兼容旧台账 |

schema v8 移除工作项和来源归属中的 `last_seen_run_id`。同步期间在内存收集本轮实际入库的工作项身份；只有完整成功且不存在更晚发起的同来源运行时才与来源归属做差集。任何更晚的同来源运行（包括仍在运行或失败的运行）都会使较早运行跳过清理，以保留新运行可能已写入的部分结果；运行收尾和清单差集仍在同一事务内提交。旧缓存首次升级先保留，由当前启用来源分别核对；多来源旧缓存需各来源完整同步后才能全部校正。详情更新已有状态摘要，不重新添加已移出清单的事项；个人待办的节点仍保留本人分配语义。

## 5. 错误分类契约（12 类 + 退出码）

| ErrorKind | 语义 | 退出码 | 用户该看什么 |
|---|---|---|---|
| Connection | DNS/TCP/TLS/超时/协议中断 | 3 | 网络 |
| Auth | 服务端拒绝凭证（401/insufficient_scope，保留 `WWW-Authenticate` 原文） | 4 | token |
| Tool | 请求送达但服务端判错（JSON-RPC error 或 `isError=true`） | 5 | 工具参数/服务端状态 |
| Parse | 有内容但形状不符（含非 JSON、未知容器——错误文本带顶层键名） | 8 | 响应结构变更 |
| Config / Credential | 配置非法 / 凭证缺失或位置不安全 | 6 / 7 | 本地配置 |
| Store | 本地 SQLite 失败 | 9 | 磁盘/文件 |
| NotImplemented | 触到预留边界（work_item_type、view、association_rule） | 10 | 本轮范围 |
| Conflict | 动作清单版本过期、该 `request_id` 已提交过、或只给编号时缓存里同一编号跨空间撞号补不出身份 ⇒ **写在发出之前就被拒** | 12 | 重新读取动作；补身份改用显式 `--project`/`--type`，不要改参数硬试 |
| Validation | 本端在发写请求前拒绝（动作不存在/已禁用/字段不认识/必填为空/选择值越界） | 13 | 动作清单与必填项 |
| Permission | 服务端**自己声明**权限不足（从错误文本识别，不自行推断） | 14 | 飞书侧权限 |
| UnknownResult | 结果不明：写可能已生效 | 15 | 先去飞书核对，**不要直接重试** |

本表是**错误类**的退出码。`fstodo workflow run` 另有两个动作结果码：`16` 动作明确失败（当前执行路径不产出，写请求一旦发出就只有 0 或 17）、`17` 动作结果不确定。17 与 15 的处置相同——先去飞书核对、不要直接重试；区别只在 15 出自错误类，17 出自动作结论。15 目前也没有产出点（`unknown_result` 只在测试里构造过），列在这里是留着「写已发出、连接断了」那类路径的归类位置，不代表现在能观察到。

判定细则：`isError=true` 是工具错误**不是空清单**；空响应载荷是解析错误**不是零条待办**；
未知容器形状（如 `{code,data}`）报解析错误并列出顶层键，**不猜测** `data/items/records`。
文本选源（2026-10-19 真实响应实测后定型）：无 `structuredContent` 时，候选按「拼接全文 → 逐非空文本块」
顺序取第一个**页形状**候选——裸数组、或含 `list` 键的对象（形状判定，不是猜字段；防止元数据块抢走数据块）。
Meego 在 JSON 数据块后追加 `log_id:` 诊断块，诊断块不得使解析失败；无一页形状时第一个对象原样上抛，
全失败时报错，消息带 serde 原因（含行列）、失败来源与截断预览。

## 6. 接口面（`api::Session`，阻塞式，供 CLI 与未来 UI 复用）

```rust
Session::open(config) -> Result<Session>          // 打开配置+缓存库（不联网、可不带凭证）
describe_credential() -> Result<String>           // 凭证来源描述（永不含值）
check_connection() -> Result<ConnectionInfo>      // 联网：新建 initialize 会话并回读服务端信息
sync_personal_todos(source_id, trigger) -> Result<SyncReport>   // trigger: manual|automatic
query_cached_items(&ItemFilter) -> Result<Vec<CachedItem>>   // 离线
count_cached_items() / last_successful_sync() / recent_runs(limit)
refresh_source_types(source_id) -> Result<TypeDiscovery>   // 联网只读发现：{ types, failed }，单个空间读失败不拖垮整次
source_types(source_id)      -> Result<Vec<CachedType>>            // 离线读快照，不联网
source_type_scope(source_id) -> Result<Option<TypeScope>>          // None = 从未确认 ⇒ 全量
set_source_type_scope(source_id, keys) -> Result<usize>            // 返回落定的（空间,类型）组合数；先核快照：没见过该键就 Validation 失败，不写入
clear_source_type_scope(source_id) -> Result<bool>                 // 回到全量的唯一路径（空集合不等于清除）
recent_actions(&WorkItemId, limit) -> Result<Vec<ActionRecord>>
call_read_tool(tool, args)（写工具拒绝）/ call_tool_any(tool, args, allow_write)
```

内部按调用创建 current-thread tokio 运行时，调用方（CLI/未来 UI）无需感知 async。
`TodoSource` trait（`describe/call_list_todo/close`）是网络侧的唯一窄接口，
测试以假实现替换即可全量覆盖同步驱动。

## 7. 配置模型（预留边界的表达方式）

| 配置 | 状态 |
|---|---|
| `kind="personal_todo"` | 唯一可执行；`action` 必填（`todo|done|overdue|this_week`），`todo_scope` 可选（`all|in_progress|not_started`），省略的可选参数**不出现在请求里** |
| `kind="work_item_type"` / `"view"` | 可保存（表达将来的空间/类型/视图配置边界），执行即 `NotImplemented`（U3 映射未核对）；启用也不参与默认选择 |
| `association_rule` | 字段预留（U2）；填非空值 → 执行前明确拒绝，**绝不静默忽略** |
| `token_env` / `token_file` | 只声明凭证*来源*；token 值不落配置文件（`deny_unknown_fields` 保证没有第三个位置） |

## 8. schema v3：类型快照、来源范围与动作台账

| 表 | 主键 | 作用与取舍 |
|---|---|---|
| `work_item_type` | `(source_id, project_key, type_key)` | `list_workitem_types` 的快照（含 `type_name`、`discovered_at_ms`）。存快照而不是每次现查，是为了让 `types list` 能离线看，也让范围选择可以按 `(空间, 类型)` 落定 |
| `source_scope_configured` | `source_id` | 区分已经配置与从未配置。已发现类型全部关闭仍保留标记；清除范围时连同范围及关闭记录一起删除 |
| `source_type_scope` | `(source_id, project_key, type_key)` | 保留旧版选中范围，供旧库迁移及保存选择时记录；schema v10 起实际同步按关闭类型集合判定 |
| `source_type_disabled`（v10） | `(source_id, type_key)` | 持续保存明确关闭的原始类型键，同一类型在各空间一起生效，新类型默认开启。旧库将已发现但未选中的类型迁入；发现结果暂时缺失某类型或修改其他类型开关时保留其关闭配置 |
| `workflow_action_run` | `request_id` | 动作流水：`item_id`（project、type、id 三元组串）、`action_kind`、`target`、`version`、`status`（`pending` / `verified` / `unknown` / `failed`）、`verified`、`detail`、`created_at`、`finished_at`。写请求发出**之前**先落 `pending`，所以超时/断连时「不知道改没改成」有证据可查；`finish_action` 只改写 `pending` 行，重复调用不会覆盖已定结论，收尾状态取值也只认 `verified` / `failed` / `unknown` |

`sync_run` 的 v3 增量见 §3。三张新表都不引用 `source(id)` 之类的外键——来源是配置文件里的
概念、没有主键表，硬加 `REFERENCES` 只会让迁移在旧库上失败（首版就是这么炸的，已全部去掉）。

范围过滤发生在**本地**：`list_todo` 的「与我相关」语义是服务端给的，本端不拿范围去改请求参数，
只在落库前筛，筛掉的数量记 `items_out_of_scope`。这样范围再怎么配都不会改变远端可见性判定。

类型开关只控制后续拉取，配置持续保留；不限制单条事项刷新或流程操作。同步完整成功后仅核对本次开启类型的来源归属，关闭类型的已有事项与来源关系保留，恢复开启后再按远端完整结果核对。

### 动作发现与执行的契约（`workflow` 模块）

| 规矩 | 依据 |
|---|---|
| 动作只从远端读接口来，绝不按节点名字猜 | `transition_node` 只认 `node_id`（模板 `state_key`），`transition_state` 只认 `transition_id` |
| 必填未齐 ⇒ 动作 `disabled` 并逐项列名 | 两个 transition 工具都不带字段值参数，本端无法代为补齐 |
| 节点动作与状态动作分开列，永不合并成「完成」 | 两条通路的写参数完全不同，合并等于替用户选一条 |
| 写之前先落 `pending`，写后必回读 | 工具返回成功 ≠ 状态真的变了 |
| `version` 不匹配 → `Conflict`（退出码 12），且发生在落 `pending` 之前 | 指纹覆盖动作集合与各自动作写参数，冲突不留尾巴 |
| 同一 `request_id` 只写一次 | `begin_action` 返回已存在即 `Conflict`，不重放 |
| 结论只有 `verified` / `unknown`（`failed` 保留但不产出） | 写请求一旦发出，说「失败」就是在催重试 |
| 只给编号时用缓存补身份，**跨空间撞号一律报冲突**（退出码 12） | 这个身份是要拿去写远端的，猜错就改了别的事项；显式 `--project`/`--type` 永远优先，缓存读不出来也照实报错，不当成「没有身份」 |
| 台账收尾只接受 `verified`/`failed`/`unknown`，其余取值直接校验失败 | 台账是幂等判断的唯一依据，留下看不懂的行等于没有证据 |
| 写后那次台账 UPDATE 失败**不改变结论**，只把这句贴在结论后面 | 把「结果不确定」降级成一个普通错误，等于藏掉最该说的话，还顺手把用户推向重试写入 |

`api::Session` 相应增加：`sync_personal_todos(source_id, trigger)`、`refresh_source_types`（返回
`TypeDiscovery { types, failed }`，单个空间读失败不拖垮整次发现）、`source_types`、
`source_type_scope`、`set_source_type_scope`（先核快照，没见过的 type_key 当场拒）、
`clear_source_type_scope`、`recent_actions`、`call_read_tool`（写工具在此层被拒）与
`call_tool_any(.., allow_write)`。
流程动作走 `workflow::actions` / `workflow::execute`，不塞进门面，避免「门面看起来什么都能写」。
