# 写侧验收手册（只由使用者本人执行）

实现侧只做过**只读**验证（动作发现、可流转表、必填表、类型清单），没有发出过任何一次写请求。
所有真写命令都要**同时**过两道闸门：配置里 `workflow_enabled = true`，命令行再显式加 `--yes`。两道闸门实现侧都不会替你越过。

## 0. 两条写入通道，两道不同的闸门

| 通道 | 闸门 | 建议顺序 |
|---|---|---|
| CLI `fstodo workflow run` | 两道都要：配置 `workflow_enabled = true` + 命令行 `--yes`。不带 `--yes` 只打印将要提交的请求，**一个字节都不发** | 先在这里验收 |
| 桌面界面 | 同一份配置的 `workflow_enabled = true`（默认 true，可设 false 关闭），界面上还要再点一次「确认执行」 | 先确认流程与字段，再执行 |

配置位置：`%APPDATA%\FSTODO\config.toml`（`fstodo doctor` 会打印实际加载路径）。

开关设为 false 时：CLI 加 `--yes` 会被直接拒（退出码 6，不会发出请求），`get_workflow_actions` /
`execute_workflow_action` 两个 IPC 也直接返回配置错误——手工构造一次 invoke 一样被拒，
不依赖前端自觉。干跑（不带 `--yes`）不需要开开关，它本来就不发请求。

## 1. 准备（全部只读）

```powershell
cd C:\Projects\FSTODO\backend
cargo build
.\target\debug\fstodo.exe doctor
.\target\debug\fstodo.exe sync
.\target\debug\fstodo.exe workflow actions <事项号>     # 记下输出的「动作清单版本」和 action id
.\target\debug\fstodo.exe actions <事项号>              # 验收前的台账基线
```

`--project` / `--type` 可省略：缓存里有这个编号的身份就自动补齐。
只有 `[可执行]` 的动作有验收意义；`[不可用]` 是 fail-closed 的结果，见第 5 节。

## 2. 用例 A：干跑必须零副作用

```powershell
.\target\debug\fstodo.exe workflow run <事项号> --action <action_id> --version <version>
$LASTEXITCODE                                       # 期望 0
.\target\debug\fstodo.exe actions <事项号>          # 期望：与基线一致，没有新行
```

判据：回显 `action_id / version / request_id / fields`，且明说「本轮没有发出任何请求」。

## 3. 用例 B：状态流转（无必填项）

```powershell
$rid = [guid]::NewGuid().ToString()
.\target\debug\fstodo.exe workflow run <事项号> --action state:<transition_id>:<目标状态> --version <version> --request-id $rid --yes
$LASTEXITCODE
```

| 退出码 | 结论 | 你要怎么核对 |
|---|---|---|
| 0 | 已核验（verified） | 飞书端状态确实变了；`fstodo sync` 后 `fstodo list` 的流程列跟着变；`actions <事项号>` 出现一行 `verified` |
| 17 | 结果不确定 | **不要重跑同一条命令。**先在飞书端看结果，台账里那行 `unknown` 就是「不知道改没改成」的证据 |
| 12 | 版本冲突 / 该 request_id 已提交过 / 只给编号时缓存里同一编号跨空间撞号 | 版本冲突：重新 `workflow actions` 取新 version；撞号：把身份写全（`--project` + `--type`），别让它猜。**两种都发生在写请求发出之前**，远端没动过 |
| 13 | 本端在发出请求前拒绝 | 动作不存在、已禁用、字段不认识、必填为空 |
| 14 | 服务端声明权限不足 | 以服务端返回的文本为准 |

`--version` 必须逐字来自**本次** `workflow actions` 的输出；中途远端动过就会 12。

## 4. 用例 C：幂等（同一 request_id 连打两次）

**这里必须换一个全新的 request_id。**`request_id` 是全局幂等键，用例 B 用过的那个已经落在台账里；
直接复用会让本用例的「第一次」也立刻被判「已提交过」——两次都返回 12，看着像通过，其实一笔都没写。

```powershell
$rid2 = [guid]::NewGuid().ToString()                # 全新，绝不复用 $rid
.\target\debug\fstodo.exe workflow actions <事项号>   # 取最新 version，替换下面的 <version>
.\target\debug\fstodo.exe workflow run <事项号> --action <action_id> --version <version> --request-id $rid2 --yes
$LASTEXITCODE                                       # 第一次：期望 0（已核验）或 17（结果不确定）
.\target\debug\fstodo.exe actions <事项号>          # 期望：$rid2 只有 1 行，且已收尾
.\target\debug\fstodo.exe workflow run <事项号> --action <action_id> --version <version> --request-id $rid2 --yes
$LASTEXITCODE                                       # 第二次：期望 12
.\target\debug\fstodo.exe actions <事项号>          # 期望：$rid2 仍然只有 1 行，第一次的结论没被改写
```

判据：第二次返回 12，且飞书端只有一笔变化。第二次的文案有两种都算对，别只看文案下结论：

- 「这个请求已经提交过，不会重复发起写操作」——幂等键先拦下；
- 动作清单版本已过期——第一次写成功后远端流程表已经变了，版本对不上，同样在发出写请求之前被拒。

两种都要回到同一处证据：台账里 `$rid2` 只有 1 行，且那一行的结论与第一次一致。

## 5. 用例 D：未支持必填项被禁用，支持项空提交被拒绝

```powershell
.\target\debug\fstodo.exe workflow actions <节点流事项号>       # 「完成节点 …」应为 [不可用] 并列出字段名
.\target\debug\fstodo.exe workflow run <节点流事项号> --action node:confirm:<节点key> --version <version> --yes
$LASTEXITCODE                                       # 期望 13
.\target\debug\fstodo.exe actions <节点流事项号>    # 期望：与基线一致（拒绝发生在落库与发送之前）
```

判据：加了 `--yes` 也必须在发出请求之前被拒。**如果真的写进去了，这是缺陷，请立刻告诉我。**

以上禁用用例应选择附件等尚不支持填写的必填类型。支持的必填字段会作为 `fields` 返回，动作可选，但不提供字段值执行时同样必须在写入前被拒绝。正式提交先更新字段并核验，再调用 `transition_node` / `transition_state`，不向流转工具塞入字段参数。

状态流单选验收：选择缺少“解决结果”的缺陷，点击“流转到「已解决」”，确认本端下拉与飞书配置一致；选择已有选项、关闭后重开应恢复草稿。点击检查不应产生远端写入，核对页显示选项名称；确认后在飞书核对字段值及目标状态，再核对本地成功回读。若字段保存或回读异常、仍缺必填、原状态已变化或流转不再可用，应停止流转并保留草稿；若字段已保存而流转结果不明，应提示这一部分结果，禁止直接重复提交。

## 6. 用例 E：节点回滚（带必填 `rollback_reason`）

```powershell
.\target\debug\fstodo.exe workflow run <节点流事项号> --action node:rollback:<节点key> --version <version> --field rollback_reason=验收用例E --yes
```

判据同用例 B。回滚的核验口径是：该节点的状态相对于**发现动作时**观察到的值发生了变化。
`rollback_reason` 直接传给回滚接口；其他支持的节点/状态必填字段通过独立的字段更新接口提交，未支持的类型仍走用例 D 的禁用路径。

## 7. 用例 F：版本冲突必须拦在写之前

```powershell
.\target\debug\fstodo.exe workflow run <事项号> --action <action_id> --version v1:deadbeefdeadbeef --yes
$LASTEXITCODE                                       # 期望 12
.\target\debug\fstodo.exe actions <事项号>          # 期望：没有多出 pending 行
```

版本校验排在「落 pending 流水」之前，所以冲突不会在台账里留下尾巴。

## 8. 打开界面通道（验收通过之后）

在 `%APPDATA%\FSTODO\config.toml` 里加一行（其余键不写就走内置默认值）：

```toml
workflow_enabled = true
```

重启应用后，详情面板出现「流程操作」的可执行动作。界面侧的验收点：

- 内联确认页要写清动作名与事项名，一次只提交一笔；
- `verified` 才出绿色结果条；`unknown` 出红色错误条并提示不要直接重试；
- 每次执行后都会重读缓存和动作清单；
- 想关闭：将这一行改为 `workflow_enabled = false`；删除这一行会恢复默认开启。

## 9. 验收完请回我这几条

1. 用例 B / E 的退出码，以及与飞书端实际结果是否一致；
2. 用例 C 是否只产生了一笔远端变化；
3. 用例 D 是否确实被 13 拒绝（且没有落 pending）；
4. 动作 label / 不可用原因的文案有没有读不懂或说得不准的地方。
