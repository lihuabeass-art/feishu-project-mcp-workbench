# 同步性能第一轮验证

验证日期：2026-10-21。范围为分阶段计时、同轮详情复用与有界并发；每轮仍获取完整清单与全部详情字段。

## 验证方式

使用正式 SQLite 的在线只读备份创建三个独立缓存副本，并复制配置到临时目录，分别设为并发 1、并发 4 和多来源并发 4。CLI 通过 `--config` 和 `--db` 指向副本，只调用飞书读取接口；正式配置和缓存未作为写入目标。

串行与并发对比依次执行同一 `related-story` 来源，均完整收到 17 条事项、1 页清单，拒绝 0 条。不是同时压测，两次执行之间网络或服务端负载仍可能变化，因此该结果是单组真实样本，不代表所有数据量下的固定提速。

## 真实接口结果

| 模式 | 同步驱动耗时 | 清单及校验 | 详情阶段 | 详情请求数 | 同轮复用 | 请求并发峰值 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 同一来源，串行 | 11,479 ms | 1,091 ms | 10,372 ms | 17 | 0 | 1 |
| 同一来源，并发 4 | 4,471 ms | 1,063 ms | 3,380 ms | 17 | 0 | 4 |
| 所有已启用来源，并发 4 | 6,563 ms | 2,717 ms | 3,687 ms | 21 | 2 | 4 |

同一来源的实际耗时减少约 61.1%，约为串行的 2.57 倍速度。详情请求累计耗时分别为 10,257 ms 和 10,604 ms，主要收益来自请求等待重叠，而非少取字段。详情写库耗时分别为 86 ms、63 ms，摘要写库均为 3 ms。

多来源收到 23 条来源记录，实际保存 21 个工作项、23 条来源归属。详情请求 21 次，两条重叠记录成功复用；两个来源均完整成功，工具层失败和取消均为 0。

串行与并发副本的复合身份、来源归属一致。接口两次返回的角色、成员和当前节点数组顺序存在差异；仅在验证脚本中按无序集合归一化这些数组及拼接节点名称后，列表摘要与完整详情内容一致。实现没有增加字段裁剪或重排远端详情。

`elapsed_ms` 不含会话关闭、IPC、页面回读与渲染；上述数字不能直接视为按钮从点击到恢复可用的完整耗时。多来源报告对各来源的驱动耗时求和，也不包含来源之间关闭会话的时间。

## 离线回归

`cargo test -- --nocapture` 共通过 147 项测试：102 项库测试、10 项来源查询测试、31 项缓存同步测试、4 项新增性能回归测试；无失败。`frontend/src-tauri` 的 `cargo check` 通过。

新增测试覆盖：

- 并发上限 1 与 4 确实生效，交错完成时仍按原清单顺序输出。
- 跨页和跨来源重复身份共用完整详情，来源归属和本人待办节点独立保留，下一轮重新获取。
- 单项详情失败不会移除旧来源归属或覆盖该项旧详情，失败详情可以在同轮后续尝试中重取，失败台账保留诊断。
- 旧 v6 缓存升级到 v7，旧运行的诊断为 null；配置默认并发 4，合法边界 1 与 8，非法值 0 与 9 被拒绝。
- 使用真实 SDK Peer 的内存传输验证两个请求同时到达、重复关闭安全、旧请求的故障不会失效替代会话。

8 条事项、单请求模拟 25～45 ms 延迟时，本次观察到串行 266 ms、并发 4 为 90 ms。测试通过实际并发峰值验证机制，不对易抖动的耗时比例设置断言。

独立 checkai 审查未发现确认缺陷。审查指出直接构造 Reader 时会将并发值限制到 1～8，主 Agent 复核后保留，确保绕过配置加载的调用同样满足并发上限；配置文件中的非法值仍明确报错。

# MCP 增量缓存与调度优化

本阶段只交付本地实现和离线验证。公司项目数据不得作为变更实验对象；收到该约束后停止所有远端访问。此前的接口探查均为读取，两轮同步使用临时缓存副本作为写入目标，没有修改飞书项目数据。以下远端能力结论仅来自已有响应，不代表完成了五类变更的真实验证。

## 版本能力与回退

| 来源 | 已有响应中的观察 | 当前策略 |
| --- | --- | --- |
| 个人待办 | 未取得可用更新时间或版本字段 | 保留详情拉取回退 |
| MQL | `update_time` 不可查询；`updated_at` 可投影但仅返回日期 | 日精度无法区分同日多次修改，保留回退 |
| 视图 | 当前没有可验证的视图配置 | 版本能力未验证，保留回退 |

字段、状态、人员、节点、排期五类变更是否都会推进版本，均未在真实事项上实验。因此当前配置不会仅凭疑似更新时间跳过详情。离线测试证明的是：可靠版本已经验证时，未变化的一轮可以零详情请求；这不是对当前公司来源的实测承诺。

缓存版本与完整详情原子保存，使用独立的 `cached_remote_version` 列；缺失版本保持未知。完整标记、待刷新标记及刷新代次共同防止不完整缓存复用，以及本地工作流修改期间旧详情请求覆盖新状态。拉取或保存失败均不推进缓存版本。

每页按“空间 + 类型 + ID”批量查询版本与刷新代次，利用详情表复合主键，不增加未使用的远端时间索引。本地清单直接读取独立的创建时间、更新时间和完成状态列，避免为每行解析完整详情 JSON。旧缓存迁移保留数据，旧详情首次按不完整处理。

## 来源核对与调度

- 来源完整扫描成功、分页结束且没有拒绝项后，才移除本轮未出现的归属；分页中断、网络或鉴权失败保留旧归属。
- 局部适配器默认只合并返回事项，不核对缺席；当前 MCP 清单适配器明确声明完整扫描。
- 未拉详情的缓存命中事项仍参与成员核对。事项移出 A、仍属于 B 时只移除 A；移出所有启用来源后从聚合清单消失。
- 所有已启用且配置完整的来源按各自成功时间、下次检查时间与失败退避调度。页面来源选择仅作显示筛选，保留“全部来源”聚合视图。
- “立即刷新”将所有可执行来源加入优先检查，与活动批次合并，缺少的来源排入后续批次。后台同步期间保留浏览与筛选。
- 后端逐来源返回检查结果和最终新增、修改、移除 patch；某来源失败仍继续其他来源。前端按复合身份合并，空 patch 保留原列表对象、选中项、搜索与滚动位置。
- 同一批次共用请求信号量和详情任务；有版本与无版本来源可以共用本批次新拉详情，明确不同的已知版本或刷新代次仍需另取，历史缓存命中不替代未知来源的详情回退。默认并发 4，合法范围 1～8。继续记录清单、详情、写库耗时及请求失败、取消、并发峰值；本阶段不自动提高并发或缩短间隔。

## 离线版本证据入口

CLI `fstodo verify-versions --source SOURCE --field FIELD --evidence FILE` 只读取本地 JSON 并保存本地验证记录，不访问远端。后续若在获准的测试环境取得可信原始样本，可以使用该入口；当前公司数据不作变更实验。

JSON 顶层必须包含 `field`、`status`、`people`、`node`、`schedule` 五项。每项结构如下，省略号需替换成该来源协议的完整原始记录和详情：

```json
{
  "before_record": { "...": "变更前原始清单记录" },
  "after_record": { "...": "变更后原始清单记录" },
  "before_detail": { "...": "变更前完整详情" },
  "after_detail": { "...": "变更后完整详情" },
  "changed_pointer": "/work_item_fields/0/value",
  "trace": "可信样本出处与变更说明"
}
```

入口使用与同步相同的字段解析逻辑，要求清单版本可读且发生变化、指针所指详情值发生变化、前后及清单/详情身份一致，并拒绝日精度日期。记录绑定当前来源配置，配置改变后自动回退。该校验不能证明样本真实性或人工标注的事件类别，操作者仍需确认五类实际变更及版本可靠性。

## 验证范围

离线回归覆盖跨轮零详情请求、少量新增/变化补拉、未知版本回退、缓存失效和保存失败、跨来源移除、局部更新不清理、并发任务复用与共享预算、迁移修复，以及前端独立调度、刷新合并、复合身份 patch 和无变化界面状态保留。

公司数据限制提出前的两轮只读同步，各取得 23 条来源记录、21 个复合身份；每轮 21 次详情请求、2 次同轮复用，并发峰值 4，工具失败/取消均为 0。驱动耗时分别 6,560 ms 和 5,934 ms。因来源没有已验证版本，两轮均走详情回退，这组样本不能用于宣称跨轮请求减少或固定提速。

最终离线检查：后端 `cargo test` 154 项通过（105 项库测试、10 项来源查询、31 项缓存同步、8 项性能回归）；前端 98 项测试通过，生产构建通过；Tauri `cargo check` 通过。独立 checkai 复审及主 Agent 复核后无遗留确认缺陷。并发与跨来源预算由性能测试专门验证，来源查询测试保持参数、分页顺序和持久化断言。
