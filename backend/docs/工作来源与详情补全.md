# 工作来源查询与单条详情补全

本说明对应 2026-10-20 的实现，替代早期文档中“类型/视图来源、关联规则尚未实现”的描述。

## 查询范围

| 来源 | 实际工具 | 筛选与分页 |
| --- | --- | --- |
| `personal_todo` | `list_todo` | 现有 action、todo_scope、asset_key；按页读取 |
| `work_item_type` | `search_by_mql` | 指定空间、任意工作项类型和关联表达式；首次执行 MQL，后续使用 session_id + group_id + page_num，不重复发 MQL |
| `view` | `get_view_detail` | 指定普通已保存视图；沿用飞书筛选条件，按页读取 |

类型来源支持全部参与人、当前参与人、指定人员字段或角色、自定义 MQL WHERE 表达式。人员字段使用远端发现的 `field_key`（`user` / `multi-user`），角色使用 `role_name`，编译为 `__角色名`。多个条件可以任一成立或全部成立。自定义规则可使用关联链、关系匹配等 MQL 函数，禁止 LIMIT、GROUP、ORDER、UNION 等查询子句与注释，以免把截断结果当全量。

类型清单筛选与来源查询是独立的：来源决定远端候选集合，用户确认的类型范围决定哪些候选需要入库和补全。没有确认类型范围时纳入全部类型；已确认空集则不取任何类型。需求和缺陷只是常见类型，不能代表飞书的全部工作项。

首次 MQL 响应读取 `list[0].count` 和唯一未分组结果，单页最多 50 条。已实测的零结果为 `list:null,data:{}`，工具无错误且有会话标识时按空结果处理；缺少分页信息、总数不一致、游标缺失或达到 max_pages 都不会记为完整成功。普通视图查询校验 pagination.total 和 has_more。未支持全景视图和分组 MQL。

## 数据结构与缓存

查询记录经完整详情补全后进入原有清单模型：复合身份（空间、类型、编号）、名称、流程摘要、排期，以及 raw_json。个人待办保留“分配给本人”的原始待办节点；其他来源由完整详情生成摘要，多个当前节点不会丢弃。

详情使用 `get_workitem_brief`，显式传 `fields:["_all"]`，按 next_page_token 获取全部页。保存结构为：

```json
{
  "id": {"project_key":"...","work_item_type_key":"story","work_item_id":"..."},
  "fetched_at_ms": 0,
  "data": {
    "work_item_attribute": {},
    "work_item_current_node": [],
    "work_item_fields": [{"key":"...","name":"...","value":{}}]
  },
  "pages": []
}
```

`data` 合并各页逻辑字段，`pages` 保留逐页原文和未知字段。SQLite v4 的 `item_detail` 表以复合身份独立保存详情，查询摘要不会覆盖详情。全页取完且复合身份核对通过后才替换快照，失败保留旧缓存。空间标识支持远端正式 key 或 simple_name；入库使用远端正式 key，并校验每一页属于同一工作项。

工作清单读取时按复合身份关联已缓存详情，返回 `created_at_ms`、`updated_at_ms` 和 `is_completed`。时间分别取自 `work_item_attribute.create_time` / `update_time`（带时区的 ISO 时间转毫秒）；完成标记只取 `work_item_fields` 中 `finish_status` 的布尔值或 `"true"` / `"false"`，缺失时保持未知。桌面清单将已完成事项放在后面，两组内按飞书更新时间倒序；没有更新时间的事项放在同组末尾，同时间按复合身份稳定排序。不会用本地首次发现、同步或详情抓取时间替代业务更新时间，历史缓存也无需重新同步即可使用已有详情参与排序。

详情面板先显示缓存再联网更新，展示概要、人员与角色、全部当前节点和业务字段；内置系统字段与未展示的基础属性收进默认折叠的「更多字段」，不丢弃任何返回值。业务字段支持图文渲染与图片预览，按需下载并在本地缓存；格式、签名下载与限制见 [业务字段图片](业务字段图片.md)。其他字段仍按文本或可展开对象展示。当前补全范围是该工具返回的逻辑字段和附件元数据，没有额外拉取评论或操作历史。

## 使用与失败处理

### 空间名称、所属项目与重叠来源（2026-10-23）

“我参与的需求”选择空间并查询全部参与人包含我的需求，在工作清单中再用“所属项目”区分同一空间内的业务项目。空间标识与所属项目关联分别保存：空间名称由 `search_project_info` 按正式 key 或 simple_name 匹配核实，不再把事项详情中不稳定的 `owned_project.name` 当作正式名称；首次核实失败显示标识及“名称未核实”，刷新失败保留上次成功目录。

“所属项目”从完整详情中“所属项目”或“所属合集”字段的实际关联值提取，并按关联字段配置中的目标空间和工作项类型读取完整项目目录。字段 key 不写死，候选包含当前没有同步事项的项目；没有提供关联字段的事项显示“未提供所属项目”，不根据空间名猜测归属。筛选按空间与项目 ID 识别项目，同一项目通过不同事项类型的关联字段引用时只显示一次；不同空间或不同 ID 的同名项目保持独立。

SQLite schema v14 从已有详情回填所属项目摘要，无需重新获取所有详情；目录存放在独立表中。别名与正式 key 的目录合并保留各类型的候选，刷新代次在数据库中校验，换 Token 或更新的刷新会作废旧请求的保存资格。目录刷新只调用读取工具，不修改飞书工作项或字段配置。

SQLite schema v17 重新从已有完整详情回填项目摘要，修复“所属合集”被遗漏的问题；迁移保留详情原文、事项身份及内容版本，不计为远端业务更新。桌面筛选仅在本次运行期间生效，两种显示模式共用当前条件，重启后全部重置，不保存或迁移筛选条件。

“全部来源”按空间 key、事项类型 key、事项 ID 展示一条工作项，来源归属另行保留。因此，同一事项同时属于个人待办和参与需求时只显示一次，仍可在任一来源下查看；不同空间或不同类型的同编号事项保持独立。单个来源的台账和 CLI 汇总统计不能直接当作去重后的清单总数；桌面整轮报告按最终唯一事项统计新增与业务更新。

### 无变化更新误报与排期范围（2026-10-23）

历史提交 `9c4a3d0`（`fix(sync): 修复刷新来源联动与无变化更新误报`）已排除响应元数据、已知集合顺序及来源间流程覆盖造成的误报。本次“无变化却更新 4 条”来自另一处范围混用：`list_todo.schedule` 是待办节点排期，详情中的 `schedule` 是事项排期；共同事项的两种排期写入同一字段，导致日期在来源切换时反复填入、清空。

SQLite schema v15 将节点排期保存在来源归属中，与本人节点流程同样按个人来源隔离；共享摘要的流程和排期统一由完整详情生成。选择个人来源时展示对应节点排期，其他来源和全部来源展示事项排期。升级时从已有详情校正共享排期，保留原始响应和详情；旧原始响应没有可靠来源归属，不推测节点排期，等待各来源实际读取后补齐。

整轮同步仍按复合身份比较前后业务差异，`patch.modified` 表示需要传给界面的缓存变化，`patch.updated_count` 表示其中确认的业务更新。首次补齐缺失的来源排期上下文只更新界面，不计作远端更新；已知节点或事项的真实改期、清空及详情正文变化仍计数。旧后端缺少该计数字段时，前端沿用原有补丁计数兼容。

只读真实复现使用正式缓存的独立副本：修复前，“我参与的需求”取得 92 条、误报更新 4 条，差异仅是四条共同事项的排期被清空；修复后同一份初始缓存查询同一来源，取得 92 条，新增 0 条、更新 0 条。回归测试覆盖两种来源交替与重复、多个个人来源的旧缓存迁移、节点与事项分别改期和清空，以及首次上下文补齐和真实变化的计数区别。

### 同步性能诊断与详情并发

完整详情落库时同时保存内容版本，清单快照和同步补丁带上该版本；正文、人员或业务字段单独变化也能通知当前打开的详情页。同步返回补丁或回读快照后，页面仅对当前事项的版本变化回读本地缓存，保留旧内容直到新快照可用，不重复请求飞书、不重建流程表单，也不主动重置阅读位置。抓取时间和分页游标变化不触发更新；旧缓存升级时回填内容版本。

所有来源同时参与调度；清单检查、完整详情和前台流程请求按端点与凭证共用[自适应请求调度器](自适应请求调度.md)的总窗口和限流反馈，分别排队并保留前台与检查位置，后台详情不能长期阻塞交互和后续来源检查。不再配置分阶段并发和请求超时。各来源仍按自身分页协议顺序翻页。无可靠版本证据的来源仍需读取详情，不能仅凭清单摘要相同判定没有变化。

普通会话打开已完成迁移的缓存时只检查结构，不执行迁移写入、旧来源认领写入或缓存清理。SQLite 必须成功启用 WAL，读取可继续看到最近已提交的完整快照；写事务使用 `BEGIN IMMEDIATE` 和 5 秒有界等待，避免先读后写的锁升级冲突。缓存清理在完整同步成功后重试，流程请求与同步使用独立会话；同事项流程写入的代次校验和幂等保护继续生效。

清单页和单项详情的字段续页仍依次读取；同一页内不同工作项的完整详情可并发获取，输出顺序保持原始清单顺序，个人待办的每条本人节点独立保留。Reader 只限制待处理任务窗口，实际网络并行度、发出间隔、退避与超时由共享调度器管理。

一次 `sync --all` 或桌面“所有已启用来源”共用一份内存详情缓存。同一复合身份在重复记录、后续清单页和其他来源中只需取得一次完整详情；只有全页取完、身份核对通过并已成功保存的详情才可复用，失败项可重试。缓存在本轮结束时释放，下轮同步仍重新取数，不根据本地时间猜测远端是否变化。各来源仍独立记录台账和核对归属。

同步报告和台账新增 `performance`，旧台账为 null，SQLite schema 升至 v7。`fstodo sync` / `fstodo runs` 显示清单及校验耗时、详情阶段耗时、详情与摘要写库耗时、详情取得与复用条数、请求并发峰值，以及按工具计数的请求耗时、失败和取消次数。请求计数包含已开始但随后取消的请求，工具层错误计入失败；解析或身份校验失败仍由同步结果表达。

`elapsed_ms` 是同步驱动实际耗时，不含会话关闭、IPC 和页面刷新；`query_ms` 包含清单查询及人员字段/角色校验，`details_ms` 包含详情写库。同步台账的工具计数和峰值统计逻辑调用，包含调度等待和内部退避，不能当作网络在途数；实际工具尝试逐次写入本地性能日志。工具请求耗时为各次逻辑调用的累计值，并发时不能相加当作实际等待时间。诊断写入失败不会覆盖业务同步结果；诊断不保存参数、响应或凭证。

MCP 会话锁仅保护初始化、替换和失效，调用期间使用 SDK 的可克隆 Peer；旧请求的延迟故障只能失效旧会话，不会关闭后来建立的新会话。传输错误和超时不自动重发，分页未取全或详情失败仍使本轮失败并保留旧归属及缓存。

首轮真实接口对比和离线回归结果见 [同步性能验证](同步性能验证.md)。

桌面端“工作来源”页面添加或编辑来源，人员规则可“发现人员字段与角色”后勾选。保存只修改本地配置，下一次同步生效；多个来源可选择“所有已启用来源”同步。各来源单独记运行台账，部分失败仍保留其他来源已取得的数据，错误包含已完成来源数和入库统计，并保留鉴权等错误分类供自动同步暂停策略使用。入库统计按来源累计，重叠工作项使用复合主键合并。

CLI 示例：

```bash
fstodo sync --source related-story
fstodo sync --all
fstodo detail 123456 --project space_key --type story
fstodo detail 123456 --project space_key --type story --cached
```

配置模板见 `backend/config.example.toml`。同步仍是增量合并缓存，本轮没有出现的旧事项不会自动删除。新增关联来源可能包含已完成工作，具体集合由选定规则和远端可见权限决定。

## 验收记录（2026-10-20）

真实只读验收使用独立配置和 SQLite 备份，不修改正式来源和正式缓存。通过实际 Rust CLI 执行 `sync --all`：

| 来源 | 完整取得 | 查询页数 | 拒绝 |
| --- | ---: | ---: | ---: |
| 缺陷：全部参与人包含我 | 55 | 2 | 0 |
| 需求：后端开发工程师角色包含我 | 13 | 1 | 0 |
| 已保存普通视图 | 10 | 1 | 0 |

累计收到 78 条来源记录；与备份中的原有缓存合并后，验收库为 69 条事项、69 份完整详情快照，各来源 total 与收到条数一致。记录间可能重叠，不能把 78 理解为 78 条不同事项。另实测“需求全部参与人包含我”为 14 条，正式库最近一次进行中个人待办仅 3 条需求，说明二者覆盖范围不同。

独立 checkai 审查无确认缺陷；字段与角色发现的 list/pagination 结构、详情续页仍带 work_item_attribute 均用真实接口核实。自动测试覆盖 MQL 51 条会话分页、零结果、缺失续页游标、人员与角色发现校验、普通视图、详情分页合并、身份不符保留缓存、结构化排期、配置保存，以及前端规则保存、缓存保留与事项切换竞态。
