# 完整检查与渐进刷新

第一轮优化保留来源完整扫描、未知版本拉取完整详情，以及整轮按空间、类型、事项 ID 计算业务差异的语义。没有扩大详情缓存有效期，也没有修改远端配额或并发上限。

## 读取与调度

当前页原始清单解析成功后，将下一页原始查询与当前页详情补全并行执行。只预取下一页，不提前补全下一页详情；MQL 的 session/group 游标仍依次使用。原始页记录详情刷新代次，详情补全继续等待对应事项的流程写入锁；本人清单跨过写入时重新读取，待保存摘要在 SQLite 事务内再次校验代次，避免批次等待期间旧摘要覆盖写后状态。

所有请求继续共享凭证对应的调度窗口、冷却与退避。后台详情发送间隔使用 `get_workitem_brief` 自身的平滑执行耗时，清单和元数据耗时不再改变它。新发起的手动刷新详情使用检查通道，后台维护使用后台通道；前台交互保留原有调度位置。加入既有后台读取时只复用任务，不重新提升其排队优先级。

## 渐进补丁与最终结果

只有完整详情已保存成功的摘要才参与提前落库；一批最多累积 8 条，独立的 100 毫秒定时分支也会发布不足一批的结果，页完成或失败前保存剩余完整结果。定时分支随当前页详情结束或取消而退出，不额外等待一个周期。原有页级写入继续负责解析、范围、收到条数与完整扫描核销。扫描不完整时仍保留原归属。

桌面 IPC 在请求开始前注册 `sync-progress` 监听；事件定向发送到发起窗口，携带请求 ID 和递增批次序号。中间补丁不移除尚未确认缺席的事项，不累计“更新 N 条”，界面持续显示正在同步。最终响应以整轮差异为基础，额外重放所有曾发布身份的当前值或删除，纠正中途改变后还原、临时新增后核销及中间事件丢失；最终提示使用独立 `changes` 计数，只统计整轮开始前和结束后的唯一事项差异。

请求结束、组件卸载、连接配置/凭证变化或流程写入开始时停止本轮事件监听。来源条件编辑继续遵循现有“下次同步使用这些条件”的约定，本轮按启动时的查询范围完成。与流程写入交叠的刷新在末尾重新读取当前缓存，避免已发出的写前补丁覆盖写后核验结果。中途失败仍读取最终缓存与失败台账，保持已有内容和明确的最终反馈。

## 在途详情复用

后台完整检查和前台详情检查共用经过凭证、数据库、复合身份、刷新代次及已知远端版本隔离的 Remote 槽。未知版本槽首次遇到已知版本时绑定该版本，两个冲突的已知版本不会重新合并。后台只加入正在执行的槽，不使用刚完成的快照替代新一轮完整检查；前台原有 1 秒短时复用期限保持不变。提交前和写后核验的强制新读取绕过这些槽。

## 诊断口径

- `requests.<tool>.elapsed_ms`：逻辑请求总耗时，包含会话、排队及重试；并发时总和可以大于整轮耗时。
- `schedule_wait_ms`：请求等待共享调度许可的耗时之和；`execution_ms`：实际工具调用执行耗时之和，含有限重试的每次执行。
- `query_ms`、`details_ms`：两阶段各自耗时，预取后可以重叠，不能相加当作整轮耗时。
- `page_wait_ms`：取得当前原始页，以及当前页详情完成后仍等待预取页的耗时。
- 批次结果的 `performance.elapsed_ms`、`first_patch_ms`、`patch_batches`：整轮结束、首个有内容补丁与发布批次数；没有变化时首补丁时间为空。固定诊断事件 `sync_first_patch`、`sync_round` 保留对应耗时。
- `detail_items_fetched` 只统计本来源实际发起的完整详情读取；跨入口在途复用计入 `detail_cache_hits`，工具请求数不重复增加。

验证只使用离线夹具和本地 HTTP mock，不向真实飞书发送探测或压测请求。
