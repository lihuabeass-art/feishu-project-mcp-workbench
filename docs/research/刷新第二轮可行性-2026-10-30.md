# 刷新第二轮可行性调查

调查日期：2026-10-30（Asia/Shanghai）。状态：研究结论，未实现第二轮能力。

用户要求：第一轮由 GPT-6.1 Sol 实施，主 Agent 继续研究第二轮能否减少远端请求。第一轮保持完整检查语义，处理调度、分页流水线、渐进补丁与在途复用；本文只研究第二轮的能力前提，不扩大第一轮实现范围。

## 判断

**仅沿用目前已核实的飞书项目 MCP 接入，尚不能可靠地做到“无变化时零详情请求”。可以批量读取部分摘要，但不能据此断言所有详情没有变化。飞书项目 OpenAPI 则已有真正的批量工作项查询契约，是减少请求次数的明确候选；接入需要另一套凭证和内容等价性验证。**

| 路线 | 已有依据 | 当前可行性 |
| --- | --- | --- |
| 前台加入后台检查时提升尚未发送的请求优先级 | 请求队列由本地调度器掌握；当前加入逻辑主要复用任务和结果 | 可继续做本地改造，改善排队时间，不减少完整检查请求数 |
| MCP 清单版本相同就跳过完整详情 | 项目已有版本门控代码；尚无当前来源的五类变更证据 | 不能直接启用 |
| MCP MQL／视图批量读取清单摘要 | 官方文档支持投影字段、按页查询 | 能研究摘要优先，但完整详情仍需核验，需明确两种新鲜度 |
| 官方 CLI `+batch-get` 替代逐条读取 | 官方源码按每个 ID 调用一次底层工具 | 不减少远端详情调用次数 |
| 每项先读操作记录／轻量详情再判断 | 官方 MCP 操作记录命令仍要求单个事项 ID | 仍是 N 次检查，变更后还要追加完整读取；收益未证实 |
| OpenAPI 按 ID 数组批量取完整内容 | 官方 SDK 有单次 POST、ID 数组、字段选择和扩展参数 | 有明确契约依据，凭证、限额、内容覆盖及性能待实测 |
| 飞书项目 Webhook 提示变化后定向回读 | 官方自动化支持多类工作项与节点事件 | 有能力依据，但需要接收服务和空间配置；仍需补偿核对 |

## 当前数据说明应优先减少调用次数

2026-10-30 17:37:27 的既有手动同步记录：MQL 来源读取 2 页及 95 份详情，驱动耗时约 9.91 秒，其中详情阶段约 8.85 秒；个人待办来源读取 1 页、18 份详情并复用 3 份同轮详情，驱动耗时约 7.53 秒。两个来源并行，不能相加作为整轮耗时。两来源合计 113 次详情调用及 3 次清单查询。

同一时间窗内详情实际尝试记录平均约 573 毫秒，P95 约 919 毫秒；同步台账中逻辑详情调用平均约 3.12 秒。两者差额约 2.55 秒/次，包含调度等额外开销，不能相加为可节省的墙钟时间。会话记录均为复用，工具没有失败。第一轮需要进一步拆分这些开销。

本轮只读检查了本机 175 份历史完整详情快照：

- 全部为 1 页，逻辑字段数中位数 21、最大 26。
- 对保存的原始详情页重新序列化，JSON 体量中位数约 4.35 KB、P95 约 6.78 KB；这不是精确 HTTP 字节数，不含协议封装，也不等于当前活跃清单样本。
- 每份详情都有 `work_item_attribute.update_time`。本地 `cached_remote_version` 非空是因为保存逻辑会从详情更新时间兜底赋值，不表示清单来源有已验证的版本能力。
- `source_version_evidence` 表记录数为 0。

因此，现有样本并非大量字段续页造成的调用膨胀。单纯缩小字段响应不改变一事项一调用的数量级；它是否缩短服务端处理时间仍需单独测量。

## 仍可在 MCP 客户端内继续优化的排队路径

第一轮会让新启动的手动检查使用检查通道，但还有一个不同的入口：自动检查已经运行时，用户点击“立即刷新”会加入该轮并等待其结果。当前 `App::run` 在这个分支主要登记手动请求范围，并没有向后端发出提升已有队列优先级的指令。共享详情槽也覆盖等待调度的时段，因此前台加入一个后台详情任务，不等于这个任务已经向飞书发送或自动获得前台优先级。

后续可以为本地排队任务增加可提升优先级的句柄：手动刷新加入时提升对应范围中尚未发送的任务；打开事项时优先发送该事项尚在排队的详情请求；已经发送的同代次请求继续合并。这条路线由客户端掌握，不要求新增飞书接口或凭证，但需要把“排队”和“已经发送”区分清楚，并维持共享限流、退避、身份／版本隔离和后台公平性。

这只能缩短用户当前关注内容的排队等待，不会把 N 次完整详情请求变成批量请求，也不能缩短已经发生的远端执行时间。应先用第一轮新增计时确认剩余等待占比，再用“已有后台长队列 + 前台加入”的确定性夹具验证优先级继承、无重复发送、取消清理与后台不被饿死。本轮未实现此能力。

代码依据：`frontend/src/App.tsx` 的 `run` 加入分支、`backend/src/remote.rs` 的共享详情槽、`backend/src/mcp/scheduler.rs` 的请求队列与优先级选择。

## 纯 MCP 路线的边界

### 可靠版本仍缺少必要证据

既有调查记录：个人待办尚未取得可靠版本字段；MQL 的 `update_time` 不可查询，`updated_at` 可投影但只有日期；视图没有完成可靠版本验证。这是历史接口观察，本轮没有重新探查当前账号的响应。

缓存中的详情更新时间需要先读取该事项才能取得，不能反过来免掉本次详情请求。可用的版本门控至少需要同时满足：

1. 能在便宜的批量清单里取得同一复合身份的版本。
2. 正文／字段、状态、人员、节点、排期的真实变化均推进该版本，清空和有效零值也覆盖。
3. 清单版本与保存详情之间的读取竞态有明确处理；写入代次变化、权限变化、异常或缺失值回退读取。
4. 来源成员继续完整核对，不能用“最近修改项”查询替代成员扫描而漏掉移出、删除或权限变化。

日期相等不能作为同日无变化证明。日期可作为未来保守热集策略的线索，例如当日事项持续检查、历史日期关闭后再核对，但仍依赖变更覆盖、时区和可见性延迟证据，不能用它绕过当前版本验证门槛。

本地入口与规则见 [同步性能验证](../../backend/docs/同步性能验证.md)、`Session::verify_source_versions`、`Store::source_version_field` 与 `SourceReader` 的版本回退逻辑。

### MQL 可以投影摘要，不能证明完整详情等价

官方 MQL 文档确认单页最多 50 条，翻页使用查询会话及分组分页参数；不支持 `SELECT *`。附件、文档等部分字段类型不能直接放入查询，另有字段只支持有限投影。节点排期也有独立访问形式，不能与事项排期混用。

因此可以研究用 MQL／视图一次取得一页清单字段，但不能对未覆盖的字段生成“完整内容无变化”结论。还需验证关联项目、完成标记、人员、节点、真实清空等清单所需信息的返回契约。

如果以后采用摘要优先，必须分别记录清单检查时间与完整详情检查时间；摘要不得覆盖完整详情，也不得更新完整详情的完成标记或指纹。打开事项的主动检查、提交前新鲜读取及写后核验继续保留。仅改变刷新提示，不能消除这些语义差异。

依据：[官方 MQL 基础语法](https://github.com/larksuite/meegle-cli/blob/51b6c92fe7bab9f830db9f4bbf2739927c434815/skills/meegle/references/mql-basics.md)、[时间与排期访问](https://github.com/larksuite/meegle-cli/blob/51b6c92fe7bab9f830db9f4bbf2739927c434815/skills/meegle/references/mql-time-status.md)、[官方性能说明](https://github.com/larksuite/meegle-cli/blob/51b6c92fe7bab9f830db9f4bbf2739927c434815/skills/meegle/references/performance.md)。

### CLI 批量命令和逐项操作记录不是变化流

官方 `+batch-get` 以固定工作池为每个 ID 发起一次工具调用，属于客户端聚合。换用 CLI 不会自动提供服务端批量详情接口。官方操作指南中的 `workitem list-op-records` 仍要求单个工作项 ID；逐项查询操作记录不能把 N 次检查变成一轮增量订阅。

同理，逐项先读取轻量详情，再对变化项读取完整详情，调用数为 N 加变化项数。只有轻量调用明显更快且版本覆盖已经验证时才可能获益，当前不能作此性能承诺。

依据：[官方批量执行源码](https://github.com/larksuite/meegle-cli/blob/51b6c92fe7bab9f830db9f4bbf2739927c434815/internal/products/meegle/batch.go)、[官方命令参数](https://github.com/larksuite/meegle-cli/blob/51b6c92fe7bab9f830db9f4bbf2739927c434815/skills/meegle/SKILL.md)。此处将技能文件作为公开接口资料阅读，未执行其中的安装、登录或业务操作。

## OpenAPI 真批量：明确的候选路径

官方 SDK 的 `GetWorkItemsByIds` 使用以下接口：

```text
POST /open_api/:project_key/work_item/:work_item_type_key/query
```

请求结构包含 `work_item_ids` 数组、`fields` 和 `expand`；响应是工作项数组。扩展结构包含流程、富文本、人员及关联字段详情等选项。返回的工作项结构包含数值 `updated_at`、当前节点、字段、流程和富文本等内容。

这说明底层有把多个事项放进一次业务请求的契约。它没有证明完整返回与 MCP 的逻辑字段聚合等价；字段权限、空值、复合字段、富文本、附件及展示名称仍需对照。SDK 中流程结构的 `version` 也不能直接视为整个事项所有业务字段的版本。

依据：[请求和响应结构](https://github.com/larksuite/project-oapi-sdk-golang/blob/f35d9ad3ad7b362722a54b16ea2697bf733ae8ee/v2/service/workitem/builder.go)、[API 方法与路径](https://github.com/larksuite/project-oapi-sdk-golang/blob/f35d9ad3ad7b362722a54b16ea2697bf733ae8ee/v2/service/workitem/api.go)、[数据和展开模型](https://github.com/larksuite/project-oapi-sdk-golang/blob/f35d9ad3ad7b362722a54b16ea2697bf733ae8ee/v2/service/workitem/model.go)。

接入候选是保留当前来源的完整成员扫描，再按空间、类型对候选事项分批读取。即使没有可靠版本，也可每轮批量完整读取，从而减少远端请求次数，并继续比较完整业务内容。

请求数可写成：

```text
当前：来源查询页数 + 唯一事项详情页数之和
批量候选：来源查询页数 + Σ ceil(每个空间/类型的事项数 ÷ 已确认批量上限)
```

公式仅说明调用数量级，不给出固定批量上限或速度保证；SDK 类型定义没有为本次调查确认接口最大批量、额度及实际吞吐。

接入前必须解决：

- OpenAPI 使用插件身份／用户插件凭证体系。官方 SDK 以 PluginID、PluginSecret 初始化，并支持用户身份请求选项；不能把现有 `X-Mcp-Token` 当成该接口的凭证。[官方 SDK 身份配置](https://github.com/larksuite/project-oapi-sdk-golang/blob/f35d9ad3ad7b362722a54b16ea2697bf733ae8ee/README.md)
- 两条连接必须核对相同用户与授权范围，不能因读取通道改变而扩大展示范围。
- 批量返回缺项不能直接判定删除。缺项可能是权限、局部失败、过滤或接口约束，须按契约处理并保留已有缓存。
- OpenAPI 数据适配不能假装是 MCP 原始响应；须保留来源，验证逻辑字段等价性并参与既有写入代次和回读保护。
- 先在授权测试环境做少量只读对照，确认内容覆盖后，再比较相同候选集合的请求数、首结果时间、整轮时间、错误率和负载。

此路线是新增读取接入能力，不是当前 MCP 适配器里的一个参数开关，本轮不实施或部署。

## Webhook：能力存在，交付条件不同

飞书项目官方文档列有字段修改、角色操作、节点状态、节点排期、工作项删除／恢复等事件。可用事件提示对应事项变脏，再通过已授权的读取通道回读。

但需要空间自动化配置以及持续可达的接收服务。桌面客户端关闭或离线时不能直接承担可靠接收；通常需要持久事件队列及客户端续接位置。事件应作为回读提示，不能直接替代完整事项真值或写后核验。

必须验证实际规则的事件覆盖，并处理重复、乱序、延迟和中断。官方自动化连接器描述的失败重推次数有限，因此仍需定期完整成员核对及详情补偿；没有收到事件不等于已证明没有变化。权限调整和视图条件变化也未被本次材料证明有完整事件覆盖。

依据：[飞书项目 Webhook](https://www.feishu.cn/content/49fq0rvm)、[自动化连接器](https://www.feishu.cn/content/ef835n76)。MCP `tools.listChanged` 仅是工具目录变化通知，不是这条业务事件通道。

## 下一步验证条件

| 验证对象 | 最小证据 | 不满足时的处理 |
| --- | --- | --- |
| 排队任务优先级继承 | 已有后台长队列中加入手动检查／前台详情后，关注项提前发送；共享预算、取消及后台公平性仍成立 | 保持当前调度，不承诺前台加入即可提速 |
| 清单版本 | 五类真实变更前后，清单版本与完整详情同时可读且覆盖变化；补充清空、连续变更及竞态 | 保留完整详情回退 |
| 批量摘要 | 相同范围下关键清单字段与完整详情一致，空值及来源节点上下文正确 | 仅作已覆盖字段的摘要，不能宣告完整无变化 |
| OpenAPI 批量详情 | 合法凭证；多类型、同 ID 不同空间、字段权限、富文本、人员、节点、排期与完整 MCP 内容对照 | 不替换当前完整详情 |
| 变化事件 | 字段／人员／节点／排期／删除等实际触发与重复、离线重连、补偿结果 | 不以事件静默作为最新性证明 |

本轮研究完成了能力与缺口的区分。第二轮若保持现有个人 MCP 凭证和完整检查语义，可先依据新增计时评估排队任务的优先级继承；若目标是进一步减少详情调用次数，仍需可靠版本或新的真批量能力。接受额外接入时，优先验证 OpenAPI 批量完整读取，再评估版本增量或事件失效通知。
