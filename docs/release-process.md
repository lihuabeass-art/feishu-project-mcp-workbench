# FSTODO 发版流程

本文件仅在用户明确要求发版，或维护发版能力时读取。准备文档、修改 CI、开发功能、验证测试，都不等于本次获准打 tag、启动发版编译或对外分发。

源码与正式安装包统一发布到公开仓库 `lihuabeass-art/feishu-project-mcp-workbench`。Windows 在本机编译，macOS 通过 GitHub Actions 编译；收齐同一 tag 的两平台完整包、updater 签名和更新清单后，先上传草稿 GitHub Release，再正式发布。软件从公开 Release 自动检查更新、后台下载并验签，准备好后提示，由用户确认重启安装；自动检查与下载可关闭。首次安装与手动恢复仍可直接下载 NSIS / DMG；软件内当前版本的更新记录继续支持离线查看。

## 正式发版的授权与完成标准

用户指定正式版本号（不含 `-beta.1` 等预发布标识）要求“发版”“发布正式版”，或要求“编译新版本”并说明“正式版本”时，按完整正式发版执行。该请求已包含推送已确认的代码及 tag、创建草稿 Release、上传附件、发布正式 Release 并设为 Latest，以及发布后的匿名验收；无需在编译结束后再次询问是否创建或发布 Release。代码提交的审查与确认仍按下文执行。

只有用户明确要求“只编译”“不发布”“暂不对外发布”等范围限制时，才停在其指定阶段。单独提交代码、日常构建或维护本流程不构成正式发版授权。

本节正式发布与 Latest 完成标准只适用于正式版本。用户指定预发布版本（如 `0.5.2-beta.1`）时，仍须按预发布类型创建并发布对应 Release，保持 `prerelease=true`，不设为 Latest、不切换正式更新源；其公开下载验收针对该版本的发布页和固定版本文件，不要求最新正式更新清单指向预发布版本。

正式发版须完成以下交付后，才能报告“发布完成”：

- 公开仓库已创建对应 tag 的 Release，且已正式发布，`draft=false`、`prerelease=false`，Latest 指向本次正式版本；不得把已有更高正式版本替换为较旧版本。
- 同一 tag、同一提交的 Windows 与 macOS 完整包、updater 签名、`latest.json`、构建元数据、更新记录和许可附件齐全，远端文件大小及 SHA256 与已核验产物一致。
- 未登录即可访问正式发布页与最新更新清单；清单指向本次版本，两个固定版本更新包均可匿名完整下载，并通过 SHA256 比对及实际签名校验。
- 向用户提供正式 Release 和安装包链接；实机安装与升级结果按实际执行情况单独记录，未执行项明确标为待验收。

仅完成本地编译、推送 tag、Actions 构建或上传草稿，均属于中间阶段。遇到阻塞时须说明尚未完成的发布步骤，不能将“编译成功”当作“发布完成”，也不能把已经获准的正式发布留待用户再次提出。

## 先确定版本号

用户必须给出本次版本号。用户只说“发版”而没有版本号时，先询问，不根据日期、当前包元数据、提交数量或 AI 判断自行递增。接受 `0.5.0`、`0.5.0-beta.1` 这样的语义化版本；本文中的版本均为操作示例。

版本 tag 通常为 `v版本号`，也兼容无 `v` 的同名版本。应用、安装包、软件内更新记录和构建产物名称都由该 tag 取版本，禁止为发版修改 `package.json`、`Cargo.toml` 或锁文件中的版本。

## GitHub 账号与非交互认证

发布仓库所属账号为 `lihuabeass-art`。同一台 Windows 电脑可能保存多个 GitHub 账号，Git Credential Manager 在没有明确账号时会弹出「Select an account」；发布自动化必须指定账号，不能让每次查询、推送或上传反复要求用户选择。

- 优先复用当前发布会话已有的 `GH_TOKEN` / `GITHUB_TOKEN`，用 `gh api user --jq .login` 核对身份为 `lihuabeass-art`，再检查仓库和 Actions 权限；不要仅凭公开仓库可读取就认定具有发布权限。
- 需要从 Git Credential Manager 读取既有凭证时，设置 `GCM_INTERACTIVE=Never`、`GIT_TERMINAL_PROMPT=0` 和 `GH_PROMPT_DISABLED=1`，向 `git credential fill` 明确提供 `protocol=https`、`host=github.com`、`username=lihuabeass-art`。推送同样使用已指定该账号的仓库 remote，并继承这些非交互设置。
- 同一次发布应在同一受控 shell 会话中将所得凭证保存在进程环境的 `GH_TOKEN`，后续 `gh` 命令直接复用；不要每调用一次 API 就重新取凭证或运行 `gh auth login`。工具启动新的 shell 时须显式继承认证环境；不得为跨调用复用而把 Token 写入仓库文件、临时脚本、命令参数或日志。
- 已有凭证可通过 `GH_TOKEN` 访问所需 API 时，直接使用环境变量。`gh auth login --with-token` 的通用 scope 检查（例如要求 `read:org`）失败，不等于该凭证无法操作本发布仓库，不应据此反复唤起登录或要求扩大无关权限。
- 明确账号后的非交互认证若仍失败，应停止需要认证的远端操作，只报告缺失账号或实际 API 权限错误；仅当确实需要人工登录时请用户处理一次，不自动反复唤起账号选择或浏览器登录。凭证值和 updater 私钥始终不得输出。

## 完整顺序（正式版本）

1. 用户明确要求发版，并指定版本号和待发布代码范围。
2. 核对分支、工作区和已存在的 tag，检查测试、功能范围、变更记录及平台限制。其他任务的未提交修改不能混入发布；不能跳过失败测试或把未核验结果写成通过。
3. 预览变更记录，核对比较起点与提交内容。自动汇总是初稿，应把提交记录与实际改动一起核对，避免把代码维护描述误当成已交付用户功能。
4. 如需提交代码，遵循仓库的 `checkai → commitsplitter → 用户确认 → 本地提交` 链路。确认发布提交后，再给该提交创建用户指定的 tag。已交付版本的 tag 不移动、不覆盖；仅对本次任务创建且尚未交付的 tag，用户要求调整本次内容时，先停止旧构建并保留旧产物，再将本次 tag 校正到经审查的提交后重建，校正前须确认远端 tag 未被他人更改。
5. 在 Windows 本机检出该 tag 对应的提交，配置 updater 签名私钥后执行 `npm run build:windows`。构建校验 tag，并生成用于软件内展示和随包交付的同一份记录。保留 NSIS、相邻 `.sig`、`release.json` 和 `RELEASE_NOTES.md`；安装包须包含本项目 `LICENSE` 与 `THIRD_PARTY_NOTICES.md`。
6. 按本次正式发版授权推送已确认的代码及该 tag；单独的本地提交请求不代表已获准推送或发布。推送版本 tag 触发 `Build macOS` 工作流。已有 tag 的手动构建或失败重跑，须填写该 tag。
7. CI 检出指定 tag 和完整历史，前端测试、macOS 后端及钥匙串测试、Universal 构建并行运行；构建生成记录、DMG，并核验架构与签名。通过 GitHub Secrets 配置同一 updater 私钥后，还须生成 Universal `.app.tar.gz` 与相邻 `.sig`；构建产物保存为 Actions Artifact，只有整次运行所有任务成功后才允许用于发布，不能仅凭构建任务成功或 Artifact 已存在继续上传。用户从构建运行中下载文件，产物保留 14 天。Actions 成功只证明构建与脚本检查通过，不能代替 Mac 实机安装验证。
8. 汇总两平台产物，核对版本、tag、提交与记录一致，按[自动更新说明](auto-update.md)生成 `latest.json`。未取得任一平台签名完整包时，不发布在线更新；不能把无签名普通安装包当作更新包。
9. 创建该 tag 的草稿 Release，上传 NSIS、Universal `.app.tar.gz`、各自 `.sig`、`latest.json`、DMG、`release.json`、更新说明及许可说明。核对附件完整、远端文件大小和 SHA256 与已核验产物一致后，将草稿作为正式 Release 一次发布，并核对 `draft=false`、`prerelease=false` 及 Latest 指向本次正式版本；草稿和预发布 Release 不作为客户端正式更新源。
10. 未登录 GitHub 验证正式 Release、最新 `latest.json` 及两个固定版本下载地址可匿名访问，核对清单中的版本与文件，完整下载两个更新包并比对 SHA256、执行实际签名校验，再向用户提供正式发布页和安装包链接。Windows 用包含 updater 的旧安装版本真实执行“自动检查 → 后台下载与验签 → 就绪提示 → 确认安装 → 重新打开”，验证前三步不抢焦点、确认前不安装，并检查关闭自动更新、手动检查、失败重试、新版本、离线记录及本机数据保留；Mac 分别记录 Actions 构建结果与实机首次安装、覆盖更新、重启及钥匙串结果。未执行的检查明确记为待验收。需要向群友发送文件或消息时，仍须有明确发送指令。

在线更新使用 Tauri 官方 updater 签名校验，自动检查与下载在后台完成，安装仍须用户明确确认；关闭窗口或正常退出不自动安装。macOS 继续使用 ad-hoc 签名，首次安装用 DMG、应用内更新用 Universal `.app.tar.gz`；updater 签名不等于 Apple Developer ID 签名或公证。分发前须核对 Gatekeeper、覆盖安装、重启及钥匙串体验；Windows 须验证旧版到新版的真实安装以及 WebView2 安装行为。macOS 的安装限制见[构建与安装说明](macos试用版构建.md)。

本机向 GitHub 上传较大的 macOS 文件发生超时，可手动运行 [Upload existing macOS release assets](../.github/workflows/upload-macos-release.yml)，填写版本 `tag`、同一 tag 的成功 `Build macOS` 运行 `run_id`，以及已有草稿的 `release_id`。工作流复用未过期的构建 Artifact，上传 Universal `.app.tar.gz` 和 DMG，不重新编译或签名；它核对运行、tag、提交、包元数据和远端摘要，已有同名完整附件且字节数、SHA256 一致时跳过，同名未完成上传或内容不一致时停止，不覆盖附件。

Windows 正式 NSIS 安装包上传同样超时，可先在本机记录原始文件的 SHA256 和总字节数，按每段 524288 字节（512 KiB）拆分，最后一段保留剩余字节，并上传至同一草稿。分段资产必须依次命名为 `FSTODO_<版本>_x64-setup.exe.part-0000`、`part-0001` 等，序号从零开始、至少四位；分段数为总字节数除以 524288 后向上取整。再次运行上述工作流，同时填写 `windows_sha256`（64 位十六进制）与 `windows_bytes`（正整数）；两项全空则跳过 Windows，不能只填其中一项。工作流只读取计算得出的确切分段名称，要求各段均已完整上传且大小正确，下载到临时目录依序拼接，核对总字节数与原始 SHA256 后，才按相同的冲突与回读规则上传正式 `.exe`；它不会执行安装包或删除远端分段。

分段仅用于草稿中转，不能出现在正式 Release。正式 Windows 包回读核验通过后，由操作者按明确资产 ID 清理本次分段并核对草稿附件；签名、清单、说明和许可文件仍须补齐，全部核验后再正式发布。清理分段后再次运行工作流时，将两项 Windows 输入留空；macOS 已有匹配附件可重复运行并跳过。该工作流本身不创建或发布 Release。

## 编译阻塞项的修复授权

用户已授权：在一次明确指定版本及范围的发版编译中，Agent 可以自主修复测试、构建和打包阻塞项，并直接提交这些修复，持续处理到 Windows 与 macOS 均编译成功，无需逐笔请求用户确认。修复仍须通过 `checkai` 独立审查、主 Agent 复核和相关验证，并由 `commitsplitter` 整理提交范围与完整中文提交信息；本授权替代上述链路中对这些阻塞修复的逐笔确认，不扩展到无关功能或其他任务的改动。

构建完成后汇报实际修复、提交和验证结果。该授权不等于允许向群友发送文件或消息，也不允许覆盖已交付的同名产物。

## 预览变更记录

在仓库 `frontend` 目录执行下面的命令，仅向终端输出初稿，不打 tag、不编译：

```sh
npm run release:notes -- --version 0.5.0
```

版本由用户先确定，命令中的 `0.5.0` 只是示例。默认比较起点是当前提交历史可达、版本号小于目标版本的最高版本 tag；按语义化版本排序，不按字符串或 tag 创建时间排序。

公开仓库从整理后的源码快照开始，原始开发历史单独私有保存。公开发版只使用本仓库可达的提交和 tag，不为生成更新记录导入私有历史；首个公开版本没有可用起点时，使用下面的首次版本介绍规则，后续版本再比较公开 tag。

- 正式版只选先前正式版作为默认起点，包含本轮 beta 阶段累计的全部变化。
- 预发布版可选先前正式版或预发布版，记录相邻测试版本的增量。
- 不在当前提交历史中的其他分支 tag 不参与比较。
- 没有符合条件的历史 tag 时，使用[首个正式版本说明](first-release-notes.md)简要介绍软件的主要功能，不罗列开发历史、内部实现和历次修复，不展示提交日期或比较起点，也不能虚构“上一版”。版本、提交和比较起点仍保留在构建元数据中供核验。

必要时，可用 `--previous-tag v0.4.3` 预览另一个已有、较低版本且历史可达的起点，以便调查范围；正式构建仍使用上述自动规则。范围有误时先调整发版方案，不用错误的比较范围继续发布。

后续版本记录从所选起点到发布提交的非合并提交标题生成，排除所有 `chore` 类型提交（包括 `chore(scope):`、`chore!:` 和 `chore(scope)!:`），再按“新增功能、问题修复、体验优化、维护与文档、其他变化”分组。软件内记录和随包 Markdown 共用这一过滤规则；范围内只有 `chore` 时，显示“当前范围没有需要展示的变更”。规范、准确的中文提交标题是生成质量的基础；无法从提交记录证明的功能、风险消除或兼容性承诺不得补写。

## 记录保存与软件展示

- `AGENTS.md` 只提供流程入口；本文件维护操作规则，不存放历次更新日志。
- 构建时生成仓库根目录下的 `artifacts/release/release.json` 和 `RELEASE_NOTES.md`，属于构建产物，不写回源码或每次追加一个版本常量。Windows 本机交付时从此目录取更新说明；macOS Artifact 已附带该文件。公开 Release 的正文与随包记录应描述同一已核对范围。
- 同一 tag、提交和完整标签历史在本机与 CI 生成相同记录。每次构建使用一份快照，校验其中的版本、tag 和提交，让软件内记录与随包 Markdown 一致；两平台汇总时再核对两份记录一致。
- `release.json` 的 `history` 保存当前构建历史可达的全部较早版本，按语义版本倒序排列，同版本的 tag 别名只保留一项。每项使用该历史 tag 自己的提交及可达的比较起点生成，包含预发布版本，不把之后的提交混入旧记录；当前版本的 Markdown 仍只描述本次变化。
- 软件侧栏的版本号可点击，默认打开当前安装版本的完整更新记录，可从版本列表切换查看各个历史版本；全部内容嵌入安装包，可离线查看，群友无需访问代码仓库。历史范围截至本次构建使用的公开 tag，不读取私有开发历史或未来版本。
- 开发提交没有发布 tag 时显示开发版本提示，同时允许查看已有公开 tag 的历史记录，不把开发代码推测成某次正式发布记录。旧的单版本构建快照在新构建中读取时兼容补齐历史。

已交付后发现说明有事实错误时，应修正来源并按新的用户指定版本重新构建，让软件内记录与交付说明一致；尚未交付的本次构建按前述内容调整规则处理。已交付产物不能被同名覆盖。

## 构建入口与核验

只有当前提交带有效版本 tag 才允许下列发版构建。以下是流程说明，本文件被读取或修改时不自动执行：

```sh
cd frontend
npm run build:windows
npm run build:macos
```

Windows 在 Windows 构建；macOS 通常使用 `.github/workflows/build-macos.yml`，也可在 Mac 本机运行对应命令。不要用独立 `tauri bundle` 给旧二进制更换版本。

### 缓存与测试调度

`Build macOS` 同时在 `main` 推送时预热缓存：前端测试使用 4 个 worker，macOS 后端测试缓存与桌面 Universal 的两种 release 架构缓存分别保存。主分支预热直接执行普通前端构建和 Cargo 编译，不打 tag、不打包、不签名或上传安装包。

Rust 缓存固定工具链并按工作区、依赖锁文件和部署目标隔离，只在 `main` 保存，发版 tag 读取默认分支缓存。GitHub 不允许不同 tag 直接复用彼此创建的缓存，因此不能只在 tag 构建里保存。缓存只复用依赖编译结果，应用本身、版本记录和安装包仍按本次 tag 重新生成；首次运行或缓存失效时自动完整编译。前端、后端、打包三个任务并行，最终发布仍要求整次运行成功。

发版核对至少包含：用户版本号与 tag 一致、无混入的未提交改动、变更比较起点正确、测试通过、两平台完整包与 updater 签名齐全、两份 `release.json` 的版本/tag/提交一致、`latest.json` 固定指向本次 tag、许可文件随包分发、软件内版本与离线记录一致、GitHub 资源可匿名下载、Windows 旧版到新版真实更新，以及单独列明的 Mac 构建和实机结果。已知测试失败须先处理，不以 CI 暂时无法运行或本机测试通过替代目标平台验证。

构建失败时先定位问题。重跑必须针对同一确认过的 tag；不能为了绕过失败而重新推送、移动 tag，不能用一个平台成功冒充两平台交付完成。
