# MCP 错误处理与用户反馈

本规范在修改 MCP 错误分类、请求重试、自动同步、详情读取或相关用户提示时读取。它约束现有飞书接入及未来其他 MCP 接入的处理方式；多厂商接入仍是候选方向，不因本文存在而视为已交付。

## 判断原则

一次请求失败、数据是否仍可使用、是否需要提醒用户，是三个不同问题。先确认失败原因与实际影响，再决定恢复方式和提示位置。后台读取短暂失败时，保留可用缓存并在受控范围内恢复；不能把所有后台失败都变成全局警报，也不能把未完成的读取或写入伪装成成功。

按以下顺序判断：

1. 是用户主动发起，还是后台维护？主动操作需要明确的最终反馈；后台请求先判断是否真的需要用户介入。
2. 影响的是当前对象、当前操作，还是其他来源或对象？只有能核对到相同复合身份的失败，才能作为当前对象的失败展示。来源里某条详情失败，不能推断该来源内所有事项都失败。
3. 是否已有可用缓存？有缓存时保留内容和上次确认时间；当前可见或用户主动关注的内容首次加载没有可用数据时，须在对应区域说明尚未取得数据，不能显示成空清单或检查成功。
4. 是可恢复的读取失败，还是需要用户处理的认证、权限、配置问题？网络超时不能冒充 Token 失效，服务过载也不能简单归咎于用户网络。
5. 是否涉及写入？写入结果不确定必须保留草稿和提交状态，先回读远端核验，不得因后台静默策略而隐去。

## 提示规则

| 场景 | 反馈方式 |
| --- | --- |
| 后台读取其他来源或对象，遇到短暂网络故障、限流或已识别的过载，已有可用数据 | 不弹全局错误；保留缓存、失败台账和受控重试，不能更新“最近成功”时间 |
| 用户主动刷新清单 | 对本次请求范围给出最终结果；失败或部分完成用简短说明，不输出服务端错误原文 |
| 用户主动打开或刷新当前事项，其独立读取失败 | 在该事项详情内显示检查失败、可用缓存时间和重试入口；不为无关来源另弹错误 |
| 当前可见或用户主动关注的内容首次加载无可用缓存 | 在对应内容区域说明加载未完成并提供恢复入口，不能伪装为空数据；未查看的后台对象不因此触发全局提示 |
| 认证失效、本机凭证不可用、权限或配置需要处理 | 用简短、可操作的提示指向连接配置或权限处理；同一问题关闭后不因每轮自动重试反复弹出，恢复或错误类别变化后再更新状态 |
| 写入失败、冲突或结果不确定 | 在对应操作或事项上下文内保留明确结果、草稿和核验入口；其它同步结果不能覆盖它，也不能自动重发写请求 |

常见文案应解释影响和下一步，例如“暂时无法获取最新信息，已保留现有内容，可稍后刷新”。不要在全局提示中拼接来源内部 ID、工具名、RPC 堆栈、服务地址、实例信息或 log ID。技术详情进入已有脱敏诊断或台账，按需在专门的诊断界面查看。

当前事项变化后，旧请求的迟到结果不得污染新事项；关闭详情后也不得再以旧对象为由打断用户。自动恢复应清除对应问题的状态，不能用其它来源的成功清除仍存在的失败。

## 主动刷新与在途请求

用户点击刷新时，可以复用同一范围内正在执行的自动读取，但必须记录这次主动关注的范围，并给出其最终反馈。不能因为底层请求最初由后台发起，就让用户主动刷新也失去结果。

如果主动请求范围是 A+B，而 A 已在执行，应复用 A 并补查 B。A 失败、B 成功时，结果仍是本次刷新未完整完成；B 的成功不能抹掉 A 的失败。范围之外的后台失败也不能污染本次主动结果。并行流程提交的成功、失败和结果不确定反馈保持独立。

## 服务适配与重试

业务错误码、文本格式和可重试标记由各服务适配层依据真实响应确认，不依赖某家厂商专有字符串作为全局规则。优先使用明确的结构化状态与错误类别；有结构化结果时，不能让附带文本覆盖其含义。`isError=true` 始终保留错误事实。

已确认的短暂故障可以接入现有共享冷却、退避与并发调度机制。重试必须有次数及总时长上限，避免请求层、同步层和界面层各自无限重试。跨来源请求应在同一服务和凭证的预算内协调；未来接入多个服务时，恢复状态应按连接及身份隔离，这是接入时的原则，不要求本次新增多服务架构。

只有已知可安全重复的只读工具允许自动重试。不能仅凭 `retriable=true`、模糊错误文案或工具名称猜测请求安全性；写工具与未知工具不自动重发。写后回读确认、结果不确定和草稿保留继续遵循 [AGENTS.md](../AGENTS.md) 的写入规则。

飞书已观测到读取请求返回 `error_code=1606`、`onDynamicOverload`、`retriable=true` 的组合。适配时应严格识别已验证的组合，再复用既有只读重试与降速机制；单独的 `1606` 或 `retriable=true` 不能推广为其它错误或其它 MCP 服务的重试依据。回归夹具使用虚构上下文，不复制真实业务数据、个人账号、内部实例地址或真实 log ID。

## 排查与验证

先对照本地台账中的时间、触发方式、来源、错误类别及后续成功记录，区分服务返回错误、本地连接失败与客户端逻辑问题。统计中的并行调用数可能包括等待调度的任务，不能直接当作远端实际收到的 HTTP 并发数，也不能仅据此认定服务过载由客户端造成。

修改相关路径时至少验证：

- 自动读取失败及恢复不反复弹出全局提示，缓存、真实失败记录和分来源退避继续工作。
- 手动刷新拒绝、部分完成和复用在途自动请求均有准确反馈，混合来源成功不能掩盖失败。
- 其它事项或来源失败不污染当前详情；当前详情失败保留缓存与时间；切换对象后迟到错误被丢弃。
- 首次无缓存、认证或权限需要处理时仍有可操作状态；关闭同类提示后自动检查不重复打扰。
- 提示使用简短用户语言，不直接展示 RPC 原文；后台结果不覆盖流程提交结论。
- 已验证的过载读取可以有限重试，普通错误不被误判；写工具和未知工具只发送一次。
- 同步业务差异、唯一事项更新计数、来源归属和写后核验继续通过原有回归。

## 参考依据

- [Microsoft InfoBar](https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/infobar)：状态提示应与用户需要关注的变化相关，避免连续反复出现和布局闪动。
- [GOV.UK Notification banner](https://design-system.service.gov.uk/components/notification-banner/)：谨慎使用全局横幅，与当前任务直接相关的信息放在对应内容中。
- [GOV.UK Error message](https://design-system.service.gov.uk/components/error-message/)：错误描述应清晰、具体，避免技术错误码与术语。
- [TanStack Query Retries](https://tanstack.com/query/latest/docs/framework/react/guides/query-retries)：按错误类型与次数控制查询重试，使用退避而非立即反复请求。此处参考恢复思路，不要求项目引入该库或照搬其默认次数。
