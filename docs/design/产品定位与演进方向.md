# 产品定位与演进方向

FSTODO 的根基是：**数据和业务规则留在原软件，FSTODO 改善人与这些数据交互的体验。** 它既可以补足已有软件缺失的体验，也可以为只有 MCP 接口的服务提供界面；用户继续使用原服务，原服务继续掌握业务数据、权限与规则。

**对于目标明确、反复执行的操作，把对象、状态、可选动作和最终值摆在眼前，可以减少反复向 AI 表达意图与核对解释的成本。** 这就是 FSTODO 为 MCP 能力提供图形界面的产品理由，展开说明见[为什么给 MCP 做图形界面](#为什么给-mcp-做图形界面)。

本文根据 2026-10-23 的产品立意与多来源 MCP 接入讨论整理，2026-10-28 补充图形交互的理由与状态边界。产品立意与判断标准用于后续取舍；多来源架构、滴答清单接入及自动识别仍是演进方向，没有因为写入本文而完成实现或获得全部实施授权。

| 范围 | 当前状态 |
| --- | --- |
| 飞书项目工作台 | 已有个人工作来源、清单与详情、本地缓存、同步、节点/状态流程操作；具体边界以[当前文档索引](../README.md)中的业务契约为准 |
| 已有基础设施 | MCP 传输、请求调度、凭证保护、动作台账、主题与桌面界面已经用于飞书；能否跨厂商直接复用仍需逐项抽取和验证 |
| 多连接、多厂商身份与存储 | 尚未实现，现有连接、凭证与事项结构仍围绕飞书 |
| 滴答清单及其他 MCP | 尚未接入；下文滴答内容是当时工具定义调查记录，不是调用成功或产品支持承诺 |
| 自动识别、声明式映射、跨来源合并视图 | 方案讨论，未交付通用自动适配能力 |

代码路径均以仓库根目录为起点。原始讨论全文已在整理前备份，下面保留立意原话、推导、演进方案与未决事项，避免把研究设想混作现有功能。

## 0. 一页结论

- **立意**：数据和业务规则留在原软件，FSTODO 只负责体验。不放弃原软件，也不替代原软件。
- **两种用法**：补位（原软件有界面但体验差）；从 0 到 1（服务只提供 MCP，没有界面）。
- **图形界面的价值**：固定、高频流程直接展示对象、状态、动作、必填字段与最终值，减少重复描述和记忆；写入仍保留核对、确认与远端回读。
- **演进基础**：已有 MCP 传输、请求调度、缓存、凭证保护、台账和界面外壳可作为复用候选；目前尚未抽成经过多厂商验证的通用适配框架。
- **关键认识**：MCP 统一的是连接和调用方式，不统一数据结构和业务含义。可以设计自动识别流程，但识别之后仍需对应适配器；当前软件没有自动适配任意 MCP 的能力。
- **设计重心**：共享外壳和基础设施，各家体验量身定制，不强求把各家数据压成统一模型。跨来源合并视图是可选项，只需要很薄的公共层。
- **范围刹车**：原软件已经做得好的就不做，一键跳回原软件。

## 1. 起因

FSTODO 最初是为了解决飞书项目卡顿、界面信息繁杂混乱、体验较差的问题：把与自己相关的需求和缺陷抓取到本地清单中显示，并能推进流程。之后考虑接入滴答清单，原因是滴答的界面不好看，也无法定制，而自己开发的软件可以自行优化性能。

由此产生的最初设想是：这个软件的核心是通过 MCP 读取数据，因此可以同时适配多家软件的 MCP，通过开关或识别 MCP 链接判断是谁家的 MCP，然后自动适配。

讨论中曾想问"有没有人做过这种软件"，后来认为真正该问的是出发点：原软件哪里让人难受，我们补哪一块。前者只能说明市场上已有什么，后者能直接决定每个功能做不做。

## 2. 立意

原话：

> 我们既可以优化软件缺失的那块体验，也实现从0到1，比如有些网站都没有界面，只是提供了mcp的接口。
> 我们不是为了放弃原来的软件。
> 也不是为了替代原来的软件。
> 数据依然存在原来的软件里面。
> 这才是我的立意。

提炼为一句话：**数据和业务规则留在原软件，FSTODO 只负责体验。**

- **补位**：原软件有界面但体验差，例如飞书项目卡顿、信息杂乱，滴答清单不好看、不能定制。FSTODO 在此基础上做减法、提速、美化。
- **从 0 到 1**：服务只提供 MCP，没有任何界面。FSTODO 为它提供第一套界面。

业界有一对现成概念可以对应：**记录系统**（System of Record）负责把数据存对、把业务规则执行对，例如飞书项目、滴答清单；**交互系统**（System of Engagement）负责让人用得顺手。FSTODO 的定位是只做交互系统，不做记录系统。

### 2.1 为什么给 MCP 做图形界面

2026-10-28 的补充原话：

> 我发现为什么mcp服务器，明明是给ai用的，我却也拿来做图形界面的原因了，因为实际上，操控ai干活，是要打字的，对于这种固定流程的操作，其实图形界面点点点，可视化，比用语言操控ai推进节点好多了

这个观察聚焦于一种具体工作：用户已经知道要处理哪条事项、完成哪项固定操作，却需要反复把这些选择重新组织成语言。语言交互也可以使用语音、预设提示或已有上下文，实际输入成本会变化；FSTODO 选择优先优化目标明确、频繁重复的流程，不据此断言所有任务都由 GUI 完成更快。

**协议依据。** MCP 的 Tools 规范以语言模型发现和调用工具为设计用途，同时明确不限定实现采用哪种用户交互模式。客户端通过 `tools/list` 发现工具，通过 `tools/call` 发起调用，因此固定界面可以把用户的明确选择映射为确定的工具参数。[MCP Tools 规范（2025-11-25）](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

架构规范将 host、client 与 server 的职责分开：host 管理连接、权限和用户授权，client 维持与特定 server 的会话并传递协议消息，server 暴露能力。图形界面是应用选择的交互入口，服务连接与业务能力仍通过客户端交互；本文对操作体验的判断是 FSTODO 的产品取舍，协议没有承诺哪一种入口更高效。[MCP Architecture（2025-11-25）](https://modelcontextprotocol.io/specification/2025-11-25/architecture)

在每次都需要用语言重新说明操作的场景中，主要成本可以拆成四部分：

| 用户需要做的事 | 图形界面如何减少重复工作 |
| --- | --- |
| 表达意图：说明想推进哪条事项、哪个节点 | 从可见清单选中对象，再从当前可用动作中选择，减少重述名称与编号 |
| 描述上下文：补充当前状态、负责人和已有字段 | 将对象状态、人员和字段放在同一界面，减少记忆与来回查找 |
| 等待理解与解释：确认系统选中了正确对象和操作 | 固定动作与业务参数建立明确映射，用户直接查看操作含义；远端读取与核验仍需要等待 |
| 复核参数：检查提交的字段和值是否符合意图 | 展示必填字段、云端当前值和最终生效值，让用户按业务范围核对 |

以推进飞书节点为例，现有界面链路是：选中事项，查看节点与可用动作，补填允许的字段并保留本机草稿，进入核对页查看本次新增、本次修改和沿用云端的最终值，再明确确认提交。后端随后重新校验云端状态，执行本次允许的差异写入，并回读验证结果。图形界面让这条链路更可见、可检查，确认与核验仍是流程的一部分；结果不确定时保留草稿，先重新读取远端状态。[字段填写与提交契约](../../backend/docs/节点填写与草稿.md)

AI 可以作为开放目标探索、跨事项分析或内容起草等场景的候选交互方式，这些任务通常需要先理解问题、整合材料或生成内容。当前 FSTODO 没有内置 AI 对话，也没有自动适配任意 MCP 的能力；这里记录选择交互方式的判断标准，不增加未来 AI 功能的实施承诺。

## 3. 判断标准

以下规则由立意推出，用于以后取舍功能。其中一部分已在现有代码中落实。

### 3.1 原软件是唯一权威，本地只是缓存

现有的几条规则本质上都是这一条的推论：写入后必须回读远端核验；结果不确定时保留草稿，提示"请先在飞书核对该事项，不要直接重试"，并且不自动重发。

[主动拉取与信息新鲜度的决策](主动拉取与信息新鲜度-设计决策.md)中“我们是主动获取，而不是飞书发消息给我们”的出发点，也来自同一个立意：数据存在别人那里，随时可能被同事或手机端修改，所以界面必须说明“截至什么时候确认过”。

### 3.2 业务数据以远端为准，本地保存缓存与个人体验

1. 远端数据的缓存，可以随时丢弃、重新获取。
2. 只属于体验的个人设置，例如视图、排序、隐藏、主题、草稿。草稿完全留在客户端本机，符合这一条。

另有连接所需的受保护凭证、同步与动作台账以及诊断日志，它们服务于运行与核验，不应悄悄变成远端业务数据的唯一副本。这里是数据归属原则，不是建议用户删除数据库；删除本地数据会丢失本机草稿、偏好与历史，凭证也可能需要重新配置。

**最容易破坏这一条的情形**：例如给飞书事项加一段"只有自己看的备注"。这段内容不会出现在飞书里，也到不了手机上。用户一旦在 FSTODO 里写下只存在本地的重要内容，FSTODO 就悄悄变成了记录系统，随之必须考虑备份和多设备同步，而这正是立意要避免的。这类功能可以做，但必须明确标为"仅本机"。

### 3.3 "回到原软件"是核心功能，不是出错时的退路

既然不替代原软件，就只需要覆盖高频操作；低频、复杂的操作让用户一键跳回原软件处理。现有代码已有这个思路：

- 流程中存在暂不支持填写的必填项时，提示"请在飞书补齐后重新读取动作"（`backend/src/workflow.rs`）。
- 需要分片下载的图片，提示"请在飞书中查看"（`backend/src/field_images.rs`）。

**演进候选**：2026-10-23 的代码盘点未找到“在飞书中打开这条事项”的直达入口；这不是对之后版本的永久断言。按立意，直达链接应成为有原界面的适配器的基础能力。按当时工具描述，滴答的 `search_task` 会返回 `url`；飞书事项的链接格式与当前入口仍需核对。

### 3.4 做减法，但不删除

飞书的痛点是信息杂乱，FSTODO 的价值在于突出与用户相关的内容。`frontend/src/detailFields.ts` 把系统字段"收进'更多字段'而不是丢弃"，就是这个分寸：可以收起来，但不能让数据从用户手里消失。

### 3.5 范围刹车

原软件已经做得好的，就不做，直接跳回去。每接入一家新来源，先写一句"它哪里让人难受、我们补哪一块"，并尽量量化，例如在原软件里找到自己的待办要点几下、等几秒。这句话就是该适配器的验收目标。

## 4. 多来源设计方向：共享外壳与基础设施，体验各自定制

讨论最初把"统一数据模型"视为最难的设计，前提是要把各家合并成一个列表。明确立意之后，目标是补体验而不是统一，重心随之调整：

- **每家有量身定制的界面**：飞书围绕"我负责的节点"和流程推进；滴答围绕美观和快速打勾。不必把两边压成同一种卡片。
- **真正共享的部分**：MCP 连接、请求调度、缓存、凭证、主题、控件和设计语言。
- **跨来源合并视图是可选项**：例如"今天要做什么"。如需实现，公共模型只需很薄一层：标题、时间（区分全天与具体时刻加时区）、是否完成、来源、跳回原软件的链接。

以下原则仍然适用：

- **外观统一，语义不统一**：滴答任务打勾即完成；飞书的一条需求，用户"完成"的只是自己负责的节点，需求本身仍在流转。两者不能使用同一种复选框。每个适配器应声明能力清单（能否打勾完成、改期、推进流程、评论等），界面按能力显示操作。前端 `Snapshot.capabilities` 已有能力开关的雏形。
- **不编造业务值、保留差异**（来自 `backend/src/model/domain.rs`）：映射不了就留空并保留原文。例如滴答的优先级 0、1、3、5 可以对应为无、低、中、高；飞书的优先级来自详情字段 `priority`，能否稳定对应这四档需要实测，对不上就不猜。
- **更新计数按适配器声明业务字段**：AGENTS.md 中"更新 N 条只按真实业务差异计数"的规则，在多来源下应由每个适配器声明哪些字段算业务变化。例如滴答的 `sortOrder`（排序值）变化是否计为一次更新，需要逐家确定。

## 5. "从 0 到 1"与"补位"的差异

立意不变，数据仍然存在对方服务中，但有三点不同：

- **没有原软件兜底**：不存在"跳回原软件"这条路，核心操作必须在 FSTODO 内完整实现。
- **没有参照界面**：无法通过原软件的展示来理解业务含义，`tools/list` 里的参数定义和工具描述是唯一的说明书，实测调查更加重要。
- **低频操作可以用自动生成的表单**：MCP 工具都带有参数的 JSON Schema，可以据此自动生成表单。现有流程表单已经按飞书返回的字段配置（`field_type`）动态生成，这个能力可以推广。但自动生成的表单更像"工具控制台"，只适合读操作和低频操作；核心操作仍需专门设计，写操作仍要经过确认和回读核验。第 7 节的声明式映射文件在这个场景最有价值，因为这类服务通常只有列表、详情和少数几个动作。

## 6. 为什么"认出是谁"不等于"自动适配好了"

MCP 可以类比为 USB 接口：USB 保证插得上、能通电、能传数据，但插上的是打印机还是摄像头，电脑仍要安装对应的驱动。MCP 保证各家的 `initialize` 握手、会话和 `tools/call` 调用方式一致，但暴露哪些工具、参数叫什么、返回什么结构，全由厂商自己定。

两家对比：

- **飞书项目**：`list_todo` 需要自行翻页；节点流和状态流两套流程模型并存；写入回执可能是纯文本 `success`；鉴权使用 `X-Mcp-Token` 请求头。
- **滴答清单**（`https://mcp.dida365.com`，原讨论当时仅记录了工具定义，未实际调用）：
  - 用 `projectId` 加 `taskId` 定位任务；
  - `status` 只有三个值：0 进行中、-1 已放弃、2 已完成；
  - `priority` 只有 0、1、3、5 四档；
  - `list_undone_tasks_by_date` 一次最多查询 14 天；
  - 清空日期需要把 `startDate`/`dueDate` 设为 `1970-01-01T00:00:00.000+0000`；
  - 时间带有 `isAllDay`（全天）和 `timeZone`（时区）。

不能仅凭服务符合 MCP 协议，就推断它的业务工具、返回格式和版本契约稳定。已观察到飞书写回执可以是纯文本，服务端也声明了 `tools.listChanged`；它表示工具列表变化，不能作为业务事项变更通知。因此每接入一家，都要重新完成实测调查、脱敏样本和契约测试，不能依赖工具名字猜业务含义。

推断：滴答 MCP 的参数结构名为 `OpenTask`、`TaskFilterOpenapi`，很可能只是对滴答开放平台 Open API 的一层封装。因此适配层宜抽象为"数据源适配器"，MCP 只是其中一种通道。`ToolResultPayload::from_json` 的注释中已经为"非 MCP 通道"留出了口子。

## 7. 自动识别方案（待实现）

按从便宜到可靠的顺序分四层逐层确认，类似电脑识别 USB 设备：先看厂商，再读设备描述，再核对支持哪些功能，最后加载驱动。

1. **看域名**：`project.feishu.cn/mcp_server/v1` 是飞书项目，`mcp.dida365.com` 是滴答。这一层不用联网，但遇到私有化部署、海外版（Lark、TickTick）或代理地址就会失效，只能当作初步猜测。
2. **看握手信息**：`initialize` 返回的 `serverInfo`，飞书实测为 `Meego MCP Server 1.0.0`。比域名可靠，但名称由厂商自填，不保证唯一，也可能变更。
3. **核对工具清单（最关键）**：调用 `tools/list`，检查适配器依赖的工具和必填参数是否齐全。具备 `list_todo`、`get_transitable_states`、`transition_node`，就交给飞书适配器；具备 `list_undone_tasks_by_date`、`complete_task` 且任务结构为 `OpenTask`，就交给滴答适配器。这一层同时是兼容性体检：厂商改了工具名或删了参数时能立即发现，降级为只读并提示用户，而不是悄悄出错。
4. **手动选择兜底**：用于识别失败或用户想强制指定的情况。

**鉴权发现**：飞书在不带凭证时返回 401，并附带 `WWW-Authenticate: Bearer resource_metadata=...`，可以顺着它找到 OAuth 授权地址。`backend/src/mcp/http.rs` 已经接住这个响应头，并转换为 `AuthRequired`。理想的接入流程是：用户粘贴链接后程序自动探测；需要授权时打开浏览器登录；握手成功后核对工具清单，再挂上对应的适配器。各家携带凭证的方式不同（飞书使用 `X-Mcp-Token` 请求头，滴答尚未实测），所以鉴权方式也属于适配器的一部分。

**陌生 MCP 的处理**：不建议在运行时让 AI 现场猜测字段含义，因为结果不确定，与"不编造业务值、写入必须回读核验"的原则直接冲突。较稳妥的做法是为简单的只读清单类来源准备一份**声明式映射文件**，写明调用哪个工具、如何翻页、哪个字段是标题、哪个字段是截止时间。映射文件可以在设计阶段由 AI 协助生成，人工审核后固定下来，运行时完全确定。复杂的写入流程（例如飞书节点推进）仍需编写代码。

## 8. 2026-10-23 的代码盘点与拟改造边界

本节保留当时的结构判断，用于说明改造规模；文件位置、行号与之后版本可能不同，实施前需重新核对。以下“可以复用”“搬入适配器”均是候选工作，没有在本文整理时完成代码迁移。

### 8.1 通用能力的复用候选

- MCP 传输层：rmcp 加上自定义的 `HttpClient`，保留了 429 限流的 `Retry-After` 和 SSE 事件大小上限（`backend/src/mcp/http.rs`）。
- 自适应请求调度器（`backend/src/mcp/scheduler.rs`）。
- 工具返回解析：`isError` 优先、`structuredContent` 优先（`backend/src/mcp/mod.rs`、`backend/src/mcp/parse.rs`）。
- 凭证加密、同步台账、以 `request_id` 防重复提交的动作台账。
- 界面外壳：主题切换、开关、下拉、紧凑模式。

`TodoSource` trait 是现成的分层接口，只是默认方法里还写着飞书的工具名（`backend/src/mcp/mod.rs` 第 100–107 行）：

```rust
async fn call_list_todo(&self, arguments: &Map<String, Value>) -> Result<ToolResultPayload, BackendError> {
```

### 8.2 写死"只有一家"、必须泛化

- **凭证与连接**：凭证表只允许存一条，名称固定为 `mcp_token`（`backend/src/store.rs` 第 1612–1615 行）；前端 `ConnectionSettings` 也只有一个 `endpoint`。接入多家需要支持多个连接、多份凭证。

  ```sql
  CREATE TABLE IF NOT EXISTS credential (
      id         TEXT PRIMARY KEY CHECK (id = 'mcp_token'),
      ciphertext BLOB NOT NULL
  );
  ```

- **事项身份**：现为 `(project_key, work_item_type_key, work_item_id)`，需要加上厂商和连接维度，否则既分不清事项来自哪里，写回时也不知道该发给谁。这与当初选择三段复合键的理由相同，只是范围再扩大一层。
- **存储结构**：`work_item` 表的 `flow_kind`、`node_name`、`node_state_key` 等列，以及前端的 `CachedItem.flow`，都是按飞书的结构设计的。
- **来源类型**：`SourceKind` 只有飞书的三种来源：个人待办、按类型查询、视图。

### 8.3 整体搬入"飞书适配器"

节点与状态流转及回读核验（`workflow.rs`、`workflow_fields.rs`）、MQL 关联规则、空间与类型目录、完整详情、字段图片。这部分代码量最大，但无需重写，只需迁移位置，并通过统一接口接入。

## 9. 性能边界

- **主要可控制的**：本地交互性能。现有缓存支持离线查看与本地筛选；长列表优化、键盘操作、自定义视图和紧凑模式可逐项改善体验。这里列的是优化方向，不能据此宣称全部已实现或已有固定性能领先结果。
- **无法掌控的**：数据新鲜度和写入确认速度。
  - 只能轮询：飞书的工具清单中没有推送或订阅类工具。
  - 查询范围有限：滴答的 `list_undone_tasks_by_date` 一次最多查 14 天，大范围需要拆成多次请求。
  - 需要防限流：已有自适应调度。
