### 原型功能点梳理

> 起点依据：[早期设计思路](../archive/设计思路.md)及[飞书项目 MCP 调查结论](../archive/飞书项目MCP调查结论.md)（2026-10-19）。用户提供的 DeskBox 截图用于材质参考，飞书截图用于说明业务入口与信息负担，均不代表需要完整复刻原产品。
>
> 产品目标与自主选择工作范围的方向已获用户认可。下文明确区分产品结论、推荐技术基线、待验证能力；待定项不能由开发者默认补齐。KPI 采用可检查的功能验收条件；对话未约定性能数值，不新增响应时间、内存或安装包体积指标。

1. **自主选择工作范围（KPI-01）** — 用户可选择进入个人工作台的业务模块，已明确举例为“需求研发”“缺陷跟踪”。验收：能够保留所选模块，仅汇总所选范围中的事项；具体模块与接口映射见 U3。
2. **筛选与本人相关的事项（KPI-02）** — 在所选工作范围内展示与本人相关的工作。验收：按已确认的关联规则核对样本，应纳入的事项能够显示、规则外事项不混入；“本人相关”的具体规则见 U2，不能仅凭待办数量判定通过。
3. **统一清单展示（KPI-03）** — 将相关需求、缺陷集中展示，减少在飞书不同页面间查找。验收：同一入口可查看所选范围内的需求与缺陷，并辨认事项类型及当前节点或状态。
4. **查看事项详情（KPI-04）** — 从清单进入单条事项详情。验收：详情对应当前所选事项，并提供判断下一步操作所需的信息；字段范围见 U4。
5. **推进流程（KPI-05）** — 在软件内操作飞书项目的流程。验收：对最终纳入范围的流程模型，展示明确的动作含义，真实操作成功后回读飞书数据，清单与远端结果一致。节点流与状态流分别验收，写侧能力见 U5。
6. **刷新与结果同步（KPI-06）** — 获取最新事项，并在流程操作后同步结果。验收：刷新后反映远端实际数据；不能在操作尚未确认成功时显示为已完成。同步时机与频率见 U6。
7. **精致的桌面视觉（KPI-07）** — 以圆角、柔和边框、磨砂或更精致的材质呈现清单。验收：在目标系统上检查真实窗口效果和文字可读性；具体材质、布局及视觉定稿见 U7。

### 板块一：模块定位

- **业务背景**：飞书工作台覆盖面广，个人只需其中与自身工作相关的部分；本软件通过自主选择工作范围，将相关事项集中为易读、可操作的个人桌面清单。
- **核心职责**：管理个人工作范围、获取相关事项、统一展示与查看详情、发起流程推进、同步远端结果，并提供精致的桌面体验。
- **最小闭环**：选择工作范围 → 汇总相关事项 → 查看详情 → 推进流程 → 同步结果。

### 板块二：核心设计决策

- **决策 1：由用户选择工作范围**
  - **背景**：原工作台包含大量模块，用户实际关注范围有限。
  - **方案**：让用户主动选择“需求研发”“缺陷跟踪”等工作来源；在所选范围内进一步筛选与本人相关的事项。

- **决策 2：工作范围与本人关联规则分层配置**
  - **背景**：选择某个模块，并不能保证其中每条事项都与本人相关；不同类型可能使用不同人员字段。
  - **方案**：分别表达“从哪里取工作”和“哪些工作属于我的关注范围”。对话中的“后端开发工程师包含我”“修复人是我”均为规则示例，具体字段与规则尚未确认，见 U2。

- **决策 3：围绕可配置工作来源组织数据接入**
  - **背景**：单一个人待办入口是否覆盖全部相关事项尚未证实。
  - **方案**：工作来源表达空间、工作项类型或视图、筛选规则及显示偏好；结合接口能力确定取数方式。禁止将所有来源固定为一个 `list_todo` 查询，也不预设左侧模块名称等于接口类型标识。

- **决策 4：需求节点流与缺陷状态流分开适配**
  - **背景**：调查记录中，需求样本具有节点信息，缺陷样本具有状态信息，两类推进接口不同。
  - **方案**：统一展示层保留流程模型差异，动作展示具体含义。按最终确认的业务范围实现对应适配；不将所有流程操作统一解释为“勾选完成”。接口行为与必填字段仍需写侧验证。

- **推荐技术基线：Tauri 2 + React + TypeScript**
  - **背景**：此前讨论以 Windows 优先、常驻桌面、可自由设计界面为推荐方向；平台范围未被用户单独确认。
  - **方案**：推荐 Tauri 2 承载桌面窗口，React + TypeScript + Vite 实现界面，Rust 本地后端负责连接、同步和流程操作；SQLite 缓存数据，凭证存系统凭据库。此处记录此前技术建议，选型整体及支持系统见 U1，具体库版本与表结构未确定。

- **推荐接入基线：直连飞书项目官方 MCP**
  - **背景**：原始思路提到飞书 CLI；调查已记录飞书项目 MCP 读侧成功，普通飞书 CLI 不覆盖该项目业务域。
  - **方案**：优先通过本地后端调用飞书项目 MCP。查询及流程按钮可直接触发确定的工具调用，核心闭环不依赖大模型。用户未单独确认 CLI 是否为强制约束，见 U8。

- **推荐视觉方向：系统材质外壳 + 清晰的清单内容**
  - **背景**：用户希望参考图中的磨砂质感，或更精致的表现。
  - **方案**：此前建议以原生窗口材质处理桌面背景，以 CSS 处理应用内部层次；候选包括 Mica、Acrylic 与纯色。窄幅清单、可展开详情、悬停操作均为候选设计，不能视为已确认原型，见 U7。

### 板块三：业务结论与待定议题记录

#### 3.1 已对齐的业务与架构结论

- **1. 产品价值**：集中处理本人相关工作，减少在飞书全面工作台中查找的成本。
- **2. 范围自主权**：用户能够挑选需要进入软件的工作模块；需求研发、缺陷跟踪是明确提到的业务范围。
- **3. 关联筛选**：进入清单的事项需要同时满足所选工作范围与本人关联条件；具体关联条件尚未确定。
- **4. 核心能力**：抓取、显示和流程推进均来自原始需求；后续讨论形成“选择范围至结果同步”的闭环方向。
- **5. 视觉目标**：软件需要好看，磨砂为明确偏好，“更高级”的具体视觉表现尚未定稿。
- **6. 现有调查证据**：根据既有调查记录，`list_todo` 读侧已成功返回个人相关需求、缺陷；这不等于已验证全部业务范围、跨空间聚合或写侧操作。本文不将既有调查描述为本轮重新实测。

### 板块四：系统边界与外部解耦

- **核心定位切分**：本软件承担个人工作聚合与操作入口。飞书保留业务数据、权限及流程约束的最终判断；飞书完整工作台中的统计卡片、质量分析、测试管理等未被确认属于本期建设范围。
- **界面与本地后端边界（推荐基线）**：界面负责范围配置、清单、详情及动作交互；本地后端负责凭证读取、外部连接、数据同步与流程调用。凭证由后端读取，不作为清单数据暴露给界面。
- **工作来源与清单边界**：来源配置负责描述业务范围及关联条件；展示层消费统一事项信息，同时保留来源标识与节点流／状态流差异。
- **数据/调用边界**：按用户选择的范围获取飞书数据，并将明确的流程动作提交给飞书。操作结果通过远端回读同步；本地显示不能替代远端成功结果。
- **大模型边界**：核心闭环可通过确定的 MCP 工具调用完成；本次未提出 AI 助手或自动决策需求。
- **缓存边界（推荐基线）**：此前建议打开先显示本地缓存、再刷新。缓存用于展示与提速；离线写入、写操作排队及自动重试策略尚无设计，不视为已授权的实现范围。

### 板块五：底层驱动与数据模型

> 本节记录已讨论的概念模型及调查中的接口字段。尚未约定数据库表名、字段类型、主键、唯一索引、迁移策略或最终 JSON Schema，不在本轮补造。

- **核心模型 1：工作来源配置（概念模型）**
  - **空间**：确定来源所在的飞书项目空间。
  - **工作项类型或视图**：表达用户选择的业务来源；与左侧入口的对应关系待核对。
  - **筛选规则**：表达本人关联条件及工作显示范围，规则语法与组合方式待定。
  - **显示偏好**：此前讨论过合并清单、按需求／缺陷分组；是否首期提供及具体配置结构待定。

- **核心模型 2：飞书个人待办返回结构（既有调查记录）**
  - `project_key` / `project_name`：来源空间标识与名称。
  - `work_item_info.work_item_id`：工作项标识。
  - `work_item_info.work_item_type_key`：工作项类型；已观测样本为 `story`、`issue`，不能据此认定覆盖全部业务类型。
  - `work_item_info.work_item_name`：工作项名称。
  - `schedule.start_time` / `schedule.end_time`：接口返回的排期字段；时间类型及本地转换约定未确定。
  - `node_info.node_name` / `node_info.node_state_key`：节点信息。
  - `state_info.start_state_key_name` / `state_info.end_state_key_name`：状态信息。
  - 上述为接口侧已观测结构，不保证直接满足最终统一清单与详情模型，缺失字段按 U4 核对。

- **核心模型 3：流程动作契约（工具元数据，行为未验证）**
  - **节点流 `transition_node`**：必填 `project_key`、`work_item_id`、`node_id`、`action`；回滚时涉及 `rollback_reason`。
  - **状态流 `get_transitable_states`**：必填 `project_key`、`work_item_id`，用于获取可流转状态信息。
  - **状态流 `transition_state`**：必填 `project_key`、`work_item_id`、`transition_id`；工具描述说明 `transition_id` 可从 `get_transitable_states` 获取。
  - **必填信息 `get_transition_required`**：必填 `state_key`；仅已知工具用于获取流转必填信息，尚未确认具体触发条件及完整调用顺序。

- **底层驱动**：此前推荐 Rust 本地 MCP 客户端连接 `https://project.feishu.cn/mcp_server/v1`。既有调查记录的 HTTP Header 模式使用 `X-Mcp-Token`，会话使用 `Mcp-Session-Id`；OAuth 元数据存在，完整登录流程未验证。具体 SDK 与持久化实现尚未选择。

### 板块六：避坑指南与防御性设计

- **界面设计原则：可滚动，但不显示原生滚动条（2026-10-19 用户确认）**
  - 全应用隐藏系统／浏览器原生滚动条，包括页面、清单、详情、弹层、文本域等滚动区域，以及横向滚动区域；不得出现粗轨道、滚动滑块、上下箭头或并排的原生滚动条。
  - 保留滚轮、触控板、触摸及键盘滚动和聚焦控件时的自动滚入可见区域。不得通过禁用滚动、裁切内容或固定高度截断来隐藏滚动条。
  - 此规则为全局默认，新增页面与组件沿用统一样式。验收覆盖长内容、嵌套滚动区域及横向溢出，确认内容仍可完整访问。

- ❌ **将个人待办当成全部本人相关工作**：既有成功样本不足以证明全部关联规则、工作类型和跨空间覆盖。
- ✅ **推荐做法**：按最终确认的来源及关联规则核对真实样本，再决定使用个人待办、类型查询或视图查询。

- ❌ **将左侧模块名称直接写死成 `story`、`issue`**：界面业务入口与接口类型、视图的映射尚未核对。
