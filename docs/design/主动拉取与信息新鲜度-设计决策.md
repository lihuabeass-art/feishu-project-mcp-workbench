# 主动拉取与信息新鲜度：事项详情的设计决策

日期：2026-10-23  
状态：已确认  
适用范围：工作清单、事项详情与刷新反馈

## 决策

保留打开事项时的自动详情检查。先展示已经保存的内容，再主动获取当前详情；界面清楚表达正在检查、检查成功或检查失败，并保留低强调的手动刷新入口。

后台约两分钟一次的定时检查与打开事项时的主动检查共同工作。定时检查维持清单的新鲜度，打开检查回应用户此刻关注这个事项的意图。

## 判断的出发点：数据由谁发起传递

本次讨论中的关键判断是：

> 我们是主动获取，而不是飞书发消息给我们。

当前产品通过主动拉取获取信息。两次成功读取之间，应用无法仅凭本地缓存知道飞书是否发生了新变化。即使后台每两分钟检查一次，用户点开事项时看到的缓存仍可能早于远端最近一次修改。

用户点开事项，是一次明确的关注行为。这个行为自然带有“我要查看它现在的情况”的预期，因此值得在此时核对一次。手动刷新按钮的使用频率，不能单独用于判断自动检查的价值。

| 信息获取方式 | 应用获得新信息的契机 | 对界面的影响 |
| --- | --- | --- |
| 定时主动拉取 | 定时器触发并成功取得数据 | 两次读取之间存在信息空窗，应显示最近成功获取的时间 |
| 用户查看时主动拉取 | 用户打开具体事项 | 对当前关注的事项重新核对，并反馈本次检查结果 |
| 服务端主动推送 | 服务端产生事件并向客户端传递 | 新鲜度取决于连接、事件覆盖和交付情况；重连或信息不完整时仍可能需要核对 |

这一区别适用于其他依赖外部信息的界面。设计刷新行为之前，应先问清楚：变化会主动到达应用，还是必须由应用发起读取才能被发现？两种机制对应的用户预期和检查时机不同。推送本身也不保证持续在线、覆盖全部字段或永不丢失事件，不能直接等同于绝对实时。

## 为什么保留打开检查

后台定时检查负责整个工作集合，用户打开检查则聚焦于一个具体事项。后者能缩短用户阅读时的信息空窗，让用户知道应用刚刚主动核对过这个事项。

一次检查取得的内容可能完全相同。它仍然提供了新的读取证据：应用在这次读取时确认了这些内容。不能仅因为业务内容相同，就把这次检查视作无意义；也不能把检查时间的变化记成“事项有更新”。

取舍是增加了一次读取及可能的等待。先展示缓存保证内容可读，检查在后台继续，避免为了核对而把现有正文清空。应优先复用确实属于同一次检查的在途请求，避免让相同事项的并行读取互相重复。

## “最新”的承诺边界

“点开后主动检查”是可兑现的行为承诺。界面只能确认截至最近一次成功读取时的信息，不能承诺远端在读取结束后不再变化。

需要区分三个时间：

- **飞书业务更新时间**：事项内容在远端发生修改的时间，继续显示在详情的“更新”字段中。
- **详情获取时间**：这份完整快照实际取得的时间，用于“已检查 · 时间”。后台成功获取的新快照也可以推进这个时间。
- **界面请求结束时间**：本地这次交互何时结束，不能拿它替代快照获取时间；读取已有缓存不能凭空生成新的远端检查时间。

打开后先展示缓存期间，界面仍然显示“正在检查最新信息…”。只有本次检查成功且当前快照可用后，才显示“已检查”；本地缓存迟到、读取成功或按钮动画结束，都不能覆盖本次联网检查的失败。

## 交互约定

| 阶段 | 展示 | 行为 |
| --- | --- | --- |
| 正在读取 | 正在检查最新信息…，刷新图标旋转 | 保留已有正文，暂时禁用手动重复触发 |
| 检查成功 | 已检查 · 最近快照获取时间 | 保留小型刷新图标，允许主动再检查；内容相同也正常结束 |
| 详情检查成功后清单摘要读取失败 | 详情继续显示已检查，单独提示清单摘要读取失败 | 保留已取得的详情，不把摘要读取错误归为远端检查失败 |
| 检查失败且有旧内容 | 检查失败；说明当前显示上次保存的信息及其获取时间 | 保留正文与手动重试入口，不宣称已确认最新 |
| 检查失败且没有旧内容 | 检查失败及原因 | 提供手动重试，不显示其他事项的旧内容 |
| 后台同步取得当前事项的新内容 | 读取已保存的新快照，更新内容及获取时间 | 不为展示同步结果再次请求飞书，不重建流程草稿或主动重置阅读位置 |

手动刷新入口使用小型图标按钮，与检查状态和时间放在一起。按钮保留可访问名称、键盘焦点、禁用状态与提示；状态变化可由辅助技术读取，动画遵循减少动态效果偏好，配色使用现有主题变量。

动画跟随真实请求。请求很快就及时结束，请求失败就展示失败，不设置虚假的最短旋转时间。动画帮助用户理解正在检查信息，不能独立作为成功依据。

## 实现范围与后续约束

本次实现调整详情反馈、手动入口和状态语义，沿用现有打开检查、后台同步和后端请求复用机制，不扩大缓存复用时间。同步与前台读取之间更广泛的在途请求合并属于后续优化，应另行验证身份、凭证、刷新代次及写入后的新鲜读取边界。

流程操作提交前仍须强制读取最新状态并在写入后核验。展示层的“已检查”、缓存时间或动画状态不能代替提交校验，也不能替代业务成功的远端回读。

后续若引入飞书事件推送，应重新评估事件覆盖、连接中断、重连补偿与缓存一致性，再决定是否调整打开检查策略。不能仅因为出现了推送通道，就删除目前提供给用户的新鲜度反馈。

## 验证重点

- 有完整缓存时仍发起打开检查，检查期间不提前显示成功。
- 业务内容无变化时正常显示检查完成，时间来自实际快照，业务更新时间保持独立。
- 联网失败后，即使本地缓存稍晚才返回，也继续显示检查失败并保留旧内容；重试成功后恢复正常状态。
- 切换事项不继承上一事项的检查结果；后台同步更新当前详情时不额外请求远端。
- 窄窗口、日间与暗黑主题、快速切换主题、键盘操作及减少动态效果下，检查状态和刷新入口均可用。
